# 逐函数覆盖审计（阶段 1 的机械补充）

> 真值：`Rich4/rich4.exe`（v3.11）。本文**全部数字由脚本现算**，可随时复跑：
>
> ```bash
> cd rich4-spec
> python3 tools/audit_spec_coverage.py            # 总览 + 分桶
> python3 tools/audit_spec_coverage.py --bucket 4 # 只看「真·遗漏」
> python3 tools/scratch/list_ui_handlers.py       # 界面处理器专项核算

## 一、为什么要做这一层

`coverage.py` 回答的是「**27 个玩法系统各写到什么程度**」，粒度是「系统」。
但「PRD 100% 覆盖原版」这句话，最终要落到**每一个函数**上：
exe 里到底有多少函数、其中哪些**一次都没被 PRD 提过**。
这一层以前只能靠人肉判断，于是出现过"系统都写完了"的错觉 ——
实测补出过 `bank.md` §4.4（破产清算后半段）与 `magic-house.md` §5.2.1
（开拍的随机消费）两处**整段缺失**。本文就是把这层判断机械化。

## 二、口径（★ 三个坑，都踩过）

1. **地址有四种写法**，只认 `0x` 前缀会系统性低估：

   | 写法 | 例 | 唯一地址数 |
   |---|---|---|
   | `0x` 前缀 | `0x0040ce0e`、`0x40ce0e` | 3,982 |
   | 反汇编器风格标注 | `fcn_00407a2c`、`loc_0043c4f5`、`sub_0040aa0f` | 39（其中 3 个是独有命中） |
   | **文档里粘贴的汇编清单**（裸 8 位） | `0040ce0e` | 6,430 |
   | 四者并集 | — | **8,745** |

   ⇒ 脚本按前三种同时扫（第四种「裸 6 位」不收：会与十进制金额混淆）。
   **第一版只认 `0x` 前缀，覆盖度被低估、未覆盖表里混进了已被文档写过的函数。**

2. **只看入口地址不够**：文档常引用函数**内部**的 `loc_0043c4f5`。
   故判据是「入口 **或** 区间 `[entry, entry+size)` 内任一地址被提到」。

3. **函数表本身有噪声**：`gen/functions.json`（1560 条）是递归遍历的产物，
   混着 CRT/运行库、Windows 窗口过程（由系统回调，天然 0 调用者）
   与遍历器的**投机候选**。不分桶的话，未覆盖表头部全是噪声。

## 四、案例：界面清单少算了 4 个处理器

`ui.md` §一 声称「这 **42 个**处理器是**权威的界面清单**」。
机械复算（`tools/scratch/list_ui_handlers.py`，沿前驱回溯、能跟 `jmp` 汇入）：

- `call 0x4018e7`（注册模态处理器）全 exe **42 处**；
- 但注册点是**多条跳转汇入共享**的（`push 0 / push <handler> / jmp <共享点>`），
  故**实际处理器 46 个**；
- `ui.md` 少列了 **5 个**：`0x42608f`、`0x4267a4`、`0x426c2e`、`0x42704e`
  （四者都汇入 `0x42839c`）、`0x434492`（汇入 `0x435e00`）。

其中 `0x434492` 读现金/存款/特別融资、带字符串「歸還款項」「週轉現金」，
与 §二 已列的**銀行貸款面板 `0x00434186` 同族**；另四个属股市/持股那一族子屏。
已在 `ui.md` §1.1 订正并补表。

> **方法学结论**：判定界面清单**必须以处理器地址为准，不能按调用点计数** ——
> 只要注册尾巴被几条路径共用，按调用点数就会系统性少算。

## 五之三、镜像审计：**PRD 写了、remake 没提**（第 51 条新增）

不是问「exe 里哪些函数 PRD 没提」，而是问
**「PRD 郑重写过的函数，remake 一次都没提到」** —— 也就是目标里

外加**同一个教训**：函数表里混着遍历器的投机候选，故按调用者数分三档。
当前结果（2026-09-16）：

| B | 0 调用者、有被调用者（回调/分支块） | 29 | 15,078 |

★ 本轮由它逼出的唯一**实质订正**不是「漏了实现」，而是**规格把一块内存认错了名字**：
`0x4967e0` 被 `ai.md`/`ui.md` 称作「持股数组（player × `0x54`，**12 档股票**）」，
实际是 **公佈欄挂牌表：4 玩家 × 7 槽 × 12 字节**（`0x54 = 7×12`）。
把**槽的字节数 12** 误当成了**股票档数**。证据：

```asm
00427edf  imul eax, dword [0x49910c], 0x54   ; 当前玩家 × 0x54
00427ee6  cmp  byte [eax + 0x496828], 0      ; 0x496828 = 0x4967e0 + 0x48 ⇒ **第 7 槽**
```

⇒ 这解释了 UI 宿主 `0x427c21` 那句 `([0x48c2ca]−0x64)/7` 与 `%7`：
**`/7` 是玩家、`%7` 是槽号**（每人 7 槽）。已在 `ai.md`/`ui.md`/`save-format.md`
三处订正，并把它从「布局未定名的 carry 块」里划掉（块本身仍走 carry —— 两个样本全 0，
但**布局已定**）。

### ★ 同一条审计查出的方法学结论：`table:code` **不能**当覆盖单位

`layout.json` 另有 64 张 `table:code`。按同一判据它们是「59/64 未被提到」，

| 类别 | 例子 | 真相 |
|---|---|---|
| **子切片** | `0x475de1`（12 项） | = 道具表 `0x475dd5` 的第 3 项起（`0x475dd5 + 3*4`，首项 `0x446c88` = 地雷）——`tools.md` 写过 |

## 六、诚实边界

- **「被提到」≠「被理解」**。本文只度量**引用**，不度量**深度**：
  一个函数可能只在表格里出现过一次地址，而它的规则细节（取整、边界、时序）
  一个字没写。真正的深度审计仍是 `gaps/*.md` 与逐系统复核。
- **`va ≥ 0x450000` 是启发式**：该区间的特征是多处 `push es`／段寄存器／
  `_libc_*` 调用链，判为 CRT；但**不能排除**里面混着少量玩法代码。
  若要更硬的界，得先厘清该区间的真实函数边界。
- **桶 2「0 调用者 + 0 被调用者」不等于幻影**：窗口过程、vtable 回调
  天然没有直接调用者；只是「两个都是 0」时可疑度最高。
- **字节占比不衡量重要性**：一个 20 字节的 `rand` 包装（`0x456f2d`）
  比 1,770 字节的绘制函数更接近规则核心。故本表用来**排优先级**，
  不用来下「已覆盖/未覆盖」的结论。
- ★ **函数表本身含「碎片」**（第 75 条新增）：`gen/functions.json` 是**递归反汇编的副产品**，
  被 `call` 目标切开的地方会留下「碎片函数」——实测 `0x4198b9` / `0x41a3be` / `0x41abde` /
  `0x41ac3c` 都是落点分派器 `0x41982d`（帧 `sub esp,0xf8`）的一部分，指向它们的
  `call|jmp` **全部来自该函数内部**。⇒ ① 逐函数覆盖率的**分母偏大**（碎片被各算一个）；
  ② 通道 2 工作单里同名的条目可能是碎片。引用时以真入口为准（判据见
  `game-loop.md` §四之二末）。
