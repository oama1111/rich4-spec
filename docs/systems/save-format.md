# 存档格式

> @source 全部来自对 `../../Rich4/rich4.exe` 的实际反汇编（`gen/db.txt`），
> 并用**两个真实存档**逐字段实证：
> `Rich4/Save0.dat`（95,371 字节）、`Rich4/SAVE1.DAT`（90,111 字节）。
>
> - 加载函数：**`VA 0x00402b27`**
> - 保存函数：**`VA 0x00403023`**（位于函数 `0x00402fd1` 内，326 条指令）
>
> 两者**块序完全对称**（同一组全局地址、同样的 `count×size`），
> 这是本表可靠性的基础 —— 偏移可由 size 直接累加校验，不依赖推测。

## 一、文件构成（★ 已完全闭合）

读档函数 `VA 0x00402ac5`（414 条指令）内共 **45 处 `fread`**。结构为：

```
存档 = [ 状态块：10,059 字节 ]
     + [ 地图结构数据：M 字节 ]                      ; M = 运行时 map_data_size
     + 对每个玩家（num_players 个）：
           [ 10,008 字节 快照 ]                      ; 時光機 的回滚块
           [ M 字节 地图数据副本 ]
```

**两个真实存档都精确闭合**（这是本结论的最强证据）：

| 存档 | 总大小 | = 状态块 | + 地图 M | + 4×(10008 + M) |
|---|---|---|---|---|
| `Save0.dat` | 95,371 | 10,059 | **9,056** | 4×(10,008+9,056) |
| `SAVE1.DAT` | 90,111 | 10,059 | **8,004** | 4×(10,008+8,004) |

两者都**分毫不差**，因此这不是推测而是解出来的唯一整数解。

### ⚠️ 两个样本存档的**地图内容差异很大**（用样本验证时的前提）

两个样本虽然都精确闭合，但它们的**地图**不是同一类：

| 存档 | 地图块大小 M | `num_map_nodes` | `num_lands` | `num_facilities` | `num_commercials` | `num_landscapes` |
|---|---|---|---|---|---|---|
| `Save0.dat` | 9,056 | 118 | **55** | 8 | 6 | 16 |
| `SAVE1.DAT` | 8,004 | 101 | **0** | 20 | 7 | 79 |

@source 头部 10 个 `uint32` 直接读自两份存档的地图块（`年` 位字段序见 `map-format.md` §二）。

**独立交叉验证**：状态块 `+0x2747` 存的正是 `map_data_size`（`@source 0x0040330d` 的
`fwrite(count=map_data_size, size=1, buf=0x47493c)`；读侧 `@source 0x00402e9b`）。
直接从两份存档的 `+0x2747` 读 `uint32` 得到 **9,056** 与 **8,004** ——
与 §一 由**文件大小闭合**反解出的 M **完全相等**。两条互不相关的路径（字段 vs 闭合）
给出同一个数，这是存档结构结论最强的证据。

**★ `SAVE1.DAT` 的 `num_lands` 是 0** —— 它是一张**没有住宅地**的地图
（`land_table_offset = 4120` 与 `facility_table_offset = 4172` 之间只有 52 字节 = `0 × 0x34`）。

> **复刻/验证时的含义**：`SAVE1.DAT` **不能**用来验证任何「地块」相关字段
> （归属、等级、租金、`flast`、`price_status` 都取不到样本）。
> 凡"用两个存档交叉验证"的结论，都要先确认该字段在**两份**里都有值；
> 只有一份有值时应标注为**单样本**。
>
> 另实测：两份存档的地图块里，住宅的 `price_status`(`+0x17`) 与 `flast`(`+0x30`)、
> 設施的 `price_status`(`+0x1c`) 与 `flast`(`+0x34`) **全部为 0** ——
> 所以这几项**无法**用现有样本验证（需要用构造数据的方式做可证伪的单测）。

### 为什么地图数据存了 5 份

- 第 1 份（`@source 0x00402ea6`）是**地图结构本体**：读入后**当场解析头部**并
  设置全部指针全局 —— 这正是 `map-format.md` 描述的加载逻辑：
  ```asm
  00402eae  mov  eax, [0x47493c]      ; 刚读入的地图缓冲
  00402eb3  mov  edx, [eax]           ; 头部字段
  00402eb5  mov  [0x498e9c], edx
  00402ebe  lea  ebx, [eax + edx]     ; base + node_table_offset
  00402ec1  mov  [0x498e80], ebx      ; ★ 节点表指针
  00402ed3  lea  ebx, [eax + edx]
  00402ed6  mov  [0x498e84], ebx      ; ★ 地产表指针
  00402eeb  mov  [0x498e88], ebx      ; ★ 商業用地表指针
  ```
- 后 4 份（`@source 0x00402f4e` / `0x00402f7b`，在按玩家循环内）是**每玩家的
  地图副本 + 10,008 字节快照**，供 **時光機**（道具 10）回滚使用 ——
  与 `tools.md` 记载的「回滚到本回合开始前的 10,008 字节快照」**完全吻合**。

> 两处独立记载（`tools.md` 的 10,008 与本节解出的 10,008）互相印证。

### 开头 4 字节 = 版本标识 `0x26`（★ 已解出，不再是缺口）

存档的**第 0..3 字节**是一个 **4 字节版本标识 = `0x26`（38）**：

| 侧 | 位置 | 行为 |
|---|---|---|
| **写** | `@source 0x00402fd7` | `mov dword ptr [esp+0x28], 0x26` —— 先备好标识值 |
| **写** | `@source 0x00403016` | `fwrite(&标识, size=4, count=1, file)` —— **最先写出的 4 字节** |
| **读** | `@source 0x00402b1a` | `fseek(file, 4, SEEK_SET)` —— **直接跳过这 4 字节，不读入内存** |

```asm
; 写：第一处 fwrite
0040300c  push  eax                  ; stream（fopen 的返回值）
0040300d  push  1                    ; count
0040300f  push  4                    ; size
00403011  lea   eax, [esp + 0x34]    ; = 子程序入口处 [esp+0x28]，即那个 0x26
00403015  push  eax                  ; buffer
00403016  call  0x457ada             ; fwrite
```
```asm
; 读：跳过
00402b16  push  esi                  ; whence = SEEK_SET（esi 已在 0x402acc 清 0）
00402b17  push  4                    ; offset = 4
00402b19  push  ebx                  ; stream
00402b1a  call  0x45753a             ; fseek
```

**A 级实证**：两个真实存档的首 4 字节**正是** `26 00 00 00`：

```
Save0.dat : 2600 0000 170a d207 0300 0000 0400 0000
SAVE1.DAT : 2600 0000 1109 d207 0300 0100 0400 0000
            ^^^^^^^^^ = 0x26，小端
```

### 逐块 `fread` 清单（42 处静态 + 3 处动态，共 45 处）

静态 42 处合计 **10,055 字节**；加上被 `fseek(4)` 跳过的 **4 字节版本标识**，
状态块 = **10,059 字节** —— 与 §一 由两个真实存档反解出的长度**精确吻合**，
**此处已无缺口**（早期版本记的"还差一处 4 字节读取"即指这 4 字节标识，
它的读取方是 `fseek` 而非 `fread`，故不在 `fread` 清单里）。

### ★ 写侧对称性校验（46 处 `fwrite`，**已逐项配对**）

保存函数 `VA 0x00402fd1`（326 条指令）内共 **46 处 `fwrite`**
（`fwrite` 是 Watcom 运行时函数 `VA 0x00457ada`，不是 Win32 导入）。
读侧 `fread` 是 `VA 0x004576d0`，共 **45 处**。

**配对结果（可复现，脚本见下）**：

- 写侧第 **1** 处写版本标识（读侧用 `fseek(4)` 跳过）；
- 写侧第 **2..46** 处 ↔ 读侧第 **1..45** 处，**一一对应，无一处错位**；
- 其中 **44** 处的 `count`/`size` 都是字面量且两侧全等
  （43 处的目标全局也是同一个字面量地址；第 44 处的缓冲是**算出来的**，
  两侧都是 `player × 0x2718` 的表达式，故比形状不比字面量）；
- 余下 **2** 处（第 43、45 处，即地图体与每玩家地图副本）的 `count`
  是运行期值 `map_data_size`（`0x498e94`），两侧都是寄存器、`size` 都是 1。

| 侧 | 处数 | 说明 |
|---|---|---|
| 写 `0x402fd1` | 46 | 第 1 处写版本标识；其余 45 处与读侧一一对应 |
| 读 `0x402ac5` | 45 | 版本标识用 `fseek(4)` 跳过，故少 1 处 |

最后 3 处是**动态尺寸**（读侧 `0x00402e9b`–`0x00402ea6`、循环体
`0x00402f23`–`0x00402f7b`；写侧 `0x00403315`–`0x0040337b`）：

| 序 | 读侧 | 写侧 | `count` | `size` | 缓冲 |
|---|---|---|---|---|---|
| 43 | `0x00402ea6` | `0x00403326` | `map_data_size`（`0x498e94`） | 1 | 地图缓冲 `0x47493c` |
| 44 | `0x00402f4e` | `0x00403363` | **1** | **`0x2718` = 10,008** | 每玩家快照，地址 = `0x48cb80 + 0x2718×玩家` |
| 45 | `0x00402f7b` | `0x0040337b` | `map_data_size` | 1 | 每玩家地图副本 |

```asm
; 写侧第 43 处（地图体）@source 0x00403315
00403315  push  ebx                  ; stream（文件句柄）
00403316  mov   ebx, dword ptr [0x498e94]   ; ebx = map_data_size
0040331c  push  ebx                  ; count = map_data_size
0040331d  push  1                    ; size = 1
0040331f  mov   esi, dword ptr [0x47493c]   ; esi = 地图缓冲
00403325  push  esi                  ; buffer
00403326  call  0x457ada             ; fwrite
```
```asm
; 写侧第 44 处（每玩家 10,008 字节快照）@source 0x00403338
00403338  push  edi                  ; stream
00403339  push  1                    ; count
0040333b  push  0x2718               ; size = 10,008
00403340  mov   eax, ebx             ; eax = 玩家下标
00403342  shl   eax, 3
00403345  add   eax, ebx             ; eax = 9 × 玩家
00403347  shl   eax, 2               ; eax = 36 × 玩家
...
00403363  call  0x457ada             ; fwrite
```

> 第 44/45 处位于**按玩家循环内**（`@source 0x0040332e`：`xor ebx,ebx` /
> `cmp ebx,[0x499114]` / `jge`），故**实际执行 num_players 次**。
> 读侧对应循环在 `0x00402f1b`–`0x00402f84`。

**复现脚本**（已实测跑通）：

```python
import sys; sys.path.insert(0, 'tools'); import rich4dis as R
d = R.Disassembler(R.Image(R.EXE_DEFAULT)); d.traverse(verbose=False, include_orphans=True)

def sites(fva, thunk):          # cdecl 压栈顺序 = stream, count, size, buffer
    fn = d.funcs[fva]; out = []
    for k, i in enumerate(fn.insns):
        if not (i.is_call and i.target == thunk): continue
        a = []
        for j in range(k - 1, -1, -1):
            p = fn.insns[j]
            if p.mnemonic == 'push': a.append(p.op_str)
            elif p.mnemonic in ('call', 'jmp') or p.mnemonic.startswith('j'): break
            if len(a) == 4: break
        a.reverse()                        # [stream, count, size, buffer]
        out.append((i.va, a))
    return out

def lit(s):
    try: return int(s, 0)
    except (ValueError, TypeError): return None

W  = sites(0x402fd1, 0x457ada)             # fwrite
Rr = sites(0x402ac5, 0x4576d0)             # fread
assert (len(W), len(Rr)) == (46, 45), (len(W), len(Rr))
stat = dyn = 0
for n, ((wv, w), (rv, r)) in enumerate(zip(W[1:], Rr), 1):
    wc, ws, wb = lit(w[1]), lit(w[2]), lit(w[3])
    rc, rs, rb = lit(r[1]), lit(r[2]), lit(r[3])
    if wc is not None and rc is not None:              # 静态：字面量全等
        assert (wc, ws) == (rc, rs), (n, hex(wv), w, hex(rv), r)
        if wb is not None:
            assert wb == rb, (n, 'buffer 不同', w, r)
        else:
            assert rb is None, (n, 'buffer 一静一动', w, r)
        stat += 1
    else:                                              # 动态：形状一致
        assert (wc is None) == (rc is None) and ws == rs, (n, w, r)
        dyn += 1
print(f'✅ 配对通过：静态 {stat} 项，动态 {dyn} 项')
# 实测输出：✅ 配对通过：静态 43 项，动态 2 项
```

> ⚠️ **一个易错点（本项目实际踩过）**：`fwrite` 的形参是
> `(buffer, size, count, stream)`，**`size` 在 `count` 之前**；
> `fread` 同样是 `(buffer, size, count, stream)`。
> 所以 §二 的表按 `count × size` 记账时，**不要按"× 项数"的印象去写**
> （`0x6c0 × 4` 与 `4 × 0x6c0` 数值相等，但语义记反会导致复刻时循环写错）。
> 另有一个实际踩过的坑：把这里的 4 个 `push` 反着读会得到
> `(stream,size,count,buffer)`，看起来"自洽"但列名全错 —— 用上面的脚本可避免。

@source 玩家数组各字段的偏移见 `economy.md` §一；本表数据直接读自两个存档文件。

### 三之二 玩家记录里六个**易错字节**（第 36 条，全部有 @source + 实测）

写档器与解析器在这几个字节上曾经不一致，而**两个样本恰好都是 0**，
所以「逐字节往返相等」这条断言在这里是**空的**。历史快照（`時光機` 槽）
与构造字节测试才把它们逼出来。

| 块内偏移 | 名称 | 类型 | 谁写 / 谁读（`@source`） | 实测 |

### 三之三 `+0x42` = **本月倒楣天數**（8 位累加器，全 exe **6 处写点**）

> 2026-09-18 补。此前 PRD **一处都没提**这个字节，remake 侧还给它起过一个错名
> （`totalWinterSleepDays`，沿自早期线索源）。真名由**月结屏**的两条字符串定死。

```asm
0043878e  push 0x1a8 / push 0x140
00438798  mov  eax, 0x464e0d              ; "本月倒楣天數："
004387a8  mov  al, byte ptr [0x48c42f]    ; 本屏要显示的那位
004387ba  imul eax, eax, 0x68
004387bd  mov  al, byte ptr [eax + 0x496baa]   ; ★ 读 +0x42
004387c9  mov  eax, 0x464e1c              ; "%d天"
```

它的第二个读点是**月度奖项评分**（`0x00437d1a`）：

```asm
00437d55  mov  bl, byte ptr [edx + 0x496baa]   ; ★ 读 +0x42
00437d5b  imul ebx, dword ptr [0x4990e8]       ; × 物价指数
00437d62  imul ebx, ebx, 0x9c4                 ; × 2500
00437d68  add  esi, ebx                        ; 加进评分
```

**6 处 8 位写点**（自扫 `add byte ptr [… + 0x496baa]`，全部是 `add`，没有别的写法）：

| # | VA | 场景 | 加多少 |
|---|---|---|---|
| 1 | `0x0040d431` | 「消失」施加函数 `0x0040d375`（命运 6/7 出國觀光・被外星人綁架；航空转盘）| 天数参数 |
| 2 | `0x0041a83f` | 住宿（旅館過路费尾段 `0x0041a3be`）| 住宿天数 |
| 3 | `0x0043d755` | 送入監獄 `0x0043d593` 的**公共尾部** | 刑期（新判与加刑都走）|
| 4 | `0x0043ee04` | 送入醫院 `0x0043ec3f` 的公共尾部 | 住院天数 |
| 5 | `0x004441a1` | 冬眠卡（card 15）：`mov dh, 5` → `add …, dh` | 5 |
| 6 | `0x00444372` | 夢遊卡（card 16）：`add byte ptr […], 5` | 5 |

外加**一处清零**：`0x00439ede`（月结收尾，见 `monthly.ts` 的 `clearMonthlyAccumulators`）。

★ 三条**易错点**（都是差分测试该钉住的）：

1. **是 8 位加法**：`add byte ptr` 会按 256 回绕。存档里它也是单字节。
2. **监狱／医院那一句在公共尾部** —— `test dh,dh / jne 加刑路径`（`0x0043d5da`）
   分出去的两支在 `0x0043d747` 汇合，所以**加刑也累加**（不是只有首次）。
   但 `0x0040d761`（首次关押清 `+0x32..+0x35` 四项）**不清** `+0x42` ——
   它是月度累加器，与那四个「当日状态」不同类。
3. **「消失」那一处只在首次分支**：`0x40d375` 的 `test ah,ah / jne 0x40d4c5`
   把「已在外」的人分去累加分支，而那一支**不加** `+0x42`。命运 6/7 的调用点
   本来就把已在外的人整个跳过（`cmp byte [+0x33],0 / jne 出去`），所以两条口径一致。

## 五、复刻要点

1. **保存与加载都必须按 §二 的块序**，不可重排 —— 位置即语义。
2. `+0x0000` 只在**写**时生成、**读**时跳过；复刻应保持同样行为。
3. 玩家数组**固定写 4 份 `0x68`**（不看实际玩家数）；
   `num_players < 4` 时仍占满 4 份槽位，复刻须照此分配与清零。
4. **加载后要重建角色指针**：`player[i].character_ref = character_profiles[player[i].character]`
   （`@source VA 0x00402b96`-`0x00402bb7`，读 `+0x13` 后查表 `0x47e80c`）。
   即存档只存**角色编号**，指针是加载时查表得出的 ——
   **这是复刻存档最容易漏的一步**。
   ★ **再往前一步（2026-09-17 补）**：新局时是**整条记录**从角色表拷来的 ——
   `@source VA 0x004072c3`-`0x004072e9`：
   ```asm
   004072cf  mov  eax, [edi + 0x48a35c]   ; [0x48a35c + 玩家×12] = 角色选择记录
   004072d5  and  eax, 0xff               ; 低字节 = 角色编号
   004072dd  add  eax, 0x47e80c           ; &character_profiles[角色]
   004072e4  call 0x456de8                ; memcpy(player, &profiles[ch], 0x68)
   ```
   ⇒ 玩家记录里凡是与角色表相同的字段（`+0x00` 名字指针、`+0x04` 代表色、
   `+0x11`/`+0x12` 移动方式/骰子数、`+0x16..0x1a` 的 AI 性格旋钮…）
   **都不是玩家状态，而是角色常量**。写档器按 `character` 查表生成即可，
   **不必给状态加字段**。`+0x00` 存进文件的其实是**进程地址**，读档即被丢弃。
   逐条证据见 `save-scalars.md` §2.17。
5. 价格历史（`0x497328`）与行情（`0x496980`）都要存；
   它们直接影响读档后的股价与物价指数行为。
6. **每玩家 10,008 字节快照的内部结构（2026-09-17 首次逐区列出）** ——
   由 `_rich4_store_current_state`（`@source 0x0044808a`，359 条指令）

   + `tools/scratch/snapshot_scalars.py`（不经 memcpy 的标量直写）。

   ★★ **两条关键结论（都会影响复刻的写档策略）**：

   **(a) 快照是「回合开始时」的历史状态，不是当前状态** ——
   实测两份真实存档：Save0 的 slot 0/1 有效标记为 1，其玩家数组与**状态块的当前玩家数组**
   相差 48 / 40 字节；slot 2/3 标记为 0（CPU 玩家从不存快照，`@source 0x004480a0`
   `test byte [player+0x15], 1 / je`）。⇒ **快照无法从当前 `GameState` 推导**，
   复刻必须自己保存「回合开始时的状态」再序列化（remake 的 `GameState.snapshots`
   存的是 JSON，正是这个用途）；**不能**把当前状态写进快照槽。

   **(b) `+0x2714` 存的是进程地址，读档时被丢弃** ——
   ```asm
   ; @source 0x00402f4e..0x00402f7b
   00402f4e  call 0x4576d0          ; fread(0x48cb80 + 10008×玩家, 0x2718, 1) ← 含文件里的旧指针
   00402f5d  call 0x456f80          ; malloc(map_data_size)
   00402f65  mov [esi + 0x48f294], eax  ; ★ 覆盖 +0x2714
   00402f7b  call 0x4576d0          ; fread(该缓冲, map_data_size, 1) ← 每玩家地图副本
   ```
   实测 Save0 四个槽的该字段是 `0x0386be50`/`0x0386e1b8`/`0x03870520`/`0x03872888`
   （同一进程内递推的堆地址），SAVE1 是 `0x02fdd4d8` 等 —— **跨进程无意义**。
   ⇒ 复刻写档时这一格**可以写 0**（原版会覆盖它），
   不必为了它去模拟堆布局。每玩家地图副本本身**仍是历史数据**（见 (a)）。
8. **地图块里的地皮/設施/企業字段是「实时状态」，不是静态数据** ——
   这一点决定了读档与写档**各自**必须做什么，两边都容易漏：

   * **读档要导入**：`land.owner/level/type/priceStatus/flast(+0x30)`、
     `facility.owner/level/type/priceStatus/flast(+0x34)`、
     **`facility.researchProject(+0x1d)` / `researchDays(+0x1e)`**、企業 `owner(+0x18)`。
     ⚠️ 研发进度这两格极易漏（它们看着像"设施的静态属性"），漏了就会
     **读档时把正在研发的設施进度清零**（`rich4-remake` 正是如此，见其
     `docs/gaps/README.md` §7.21）。
   * **写档要先合并**：把 `GameState` 里的实时值覆盖回地图模板再交给写档器。
     否则写出的是**装载那一刻**的归属 —— 而"读进来再原样写回去"这条测试
     **恰好测不出来**（那一刻两者相同）。
   * 企業归属的实时值来自持股排名（`_rich4_update_commercial_owner`），
     不是持股本身的某个字段。

7. **`+0x2714` 之后紧跟每玩家的地图副本**（`map_data_size` 字节），
   与 `+0x2714` 里的指针配对；`save-format.md` §一 的「4×(10008 + M)」闭合公式
   指的就是「10008 字节槽 + M 字节地图副本」这一对。
