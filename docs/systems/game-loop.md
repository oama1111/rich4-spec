# 回合流程 · 主循环 · 核心基建

> 本文件是全项目的**接线骨架**。所有其它系统（卡片/道具/新闻/股市…）都挂在
> 这里的某个点上。`@source` 均为原版虚拟地址。

## 一、程序骨架

@source PE 入口点 `0x45709c`（`jmp 0x458ced`）；`0x458ced` 的 5 个调用目标。

```
PE 入口点 0x45709c
   └─ jmp 0x458ced                 ; CRT 启动：栈探测、__setargv、堆初始化
        ├─ call 0x45abd6           ; 栈探测 / 堆初始化
        ├─ call 0x458859           ; CRT 初始化（内部再调 0x4585ef / 0x45a666 / 0x45ab58）
        └─ …                       ; 最终进入 WinMain（见 §三）
```

⚠️ **从 PE 入口点静态只能到达 23 个函数。** 游戏主体是通过**间接调用**
（`jmp_indirect`、COM 虚表、`SetTimer` 回调、窗口过程）进入的，
**不能靠从入口点做递归遍历来发现游戏逻辑**。这是本项目定位主循环时踩过的坑。

### 内嵌模态消息泵 `0x004018e7`（127 字节，被调用 **19 处**）

@source `VA 0x004018e7` - `0x00401965`（完整指令见下方摘录）。

这是**任何等待玩家操作的模态界面**都在用的内嵌消息循环：

```asm
004018eb  mov  edx, [0x46cad8]        ; 消息泵嵌套深度计数器
004018f1  inc  edx
004018f2  mov  [0x46cad8], edx
004018fe  mov  [eax*4 + 0x48a010], edx ; ★ 把「当前层级的消息过滤器」压入栈
00401918  call dword ptr cs:[0x462310] ; PeekMessage 相关（0x462310）
0040192c  call dword ptr cs:[0x46230c] ; ★ PeekMessageA
00401935  je   0x40191f                ; 无消息 → 继续轮询（忙等）
00401937  cmp  dword ptr [esp+4], 0x402
0040193f  je   0x401957                ; ★ WM_QUIT(0x402) → 退出循环
00401944  call dword ptr cs:[0x462334] ; TranslateMessage
0040194e  call dword ptr cs:[0x4622e0] ; DispatchMessageA
00401957  dec  dword ptr [0x46cad8]    ; 退出时弹层
```

**语义**：这是一个 `while (PeekMessage) { if (WM_QUIT) break; Translate; Dispatch; }`
的**忙等**循环。它维护一个**嵌套深度**（`0x46cad8`）与一个**层级消息过滤器数组**
（`0x48a010[level]`）。

> **复刻要点**：多个模态界面可以嵌套（例如「卖地」界面里又弹出确认框）。
> 复刻时必须保留嵌套语义，否则深层弹窗返回后无法正确恢复到上层。

### WndProc 的分派结构（`0x4019dd`，90 条指令）

@source `VA 0x004019dd`；消息判定在 `0x004019e1`-`0x00401a05`。

```asm
004019e1  mov  eax, [esp+0x18]        ; msg
004019eb  cmp  eax, 0x1c              ; WM_ACTIVATEAPP(0x1c)
004019ee  jb   0x401a02
004019f0  jbe  0x401a10
004019f2  cmp  eax, 0x3b9             ; ★ 自定义消息 0x3b9
004019f7  je   0x401b08
004019fd  jmp  0x401b33               ; 默认：DefWindowProc
00401a02  cmp  eax, 2                 ; WM_DESTROY
00401a05  je   0x401b24
```

处理的消息（实测）：`WM_DESTROY(2)`、`WM_ACTIVATEAPP(0x1c)`、自定义 `0x3b9`。

`WM_ACTIVATEAPP` 分支（`0x401a10`）在**激活**时做 DirectDraw 表面恢复：
```asm
00401a21  mov  esi, [0x48a0dc]        ; DirectDraw 主接口
00401a2b  mov  edx, [esi]             ; ★ 虚表指针
00401a2e  call dword ptr [edx + 0x6c] ; COM 虚方法（vtable 偏移 0x6c）
```
这是 **COM 虚表调用**，静态不可解析 —— 也是"从入口点遍历到不了游戏逻辑"的原因之一。

`WM_DESTROY` 分支以 `call 0x401815` 收尾，随后 `call [0x462314]`（`PostQuitMessage`）。

## 三、游戏推进：**定时器驱动**，不是主循环驱动

原版**没有**"一个主循环里跑回合"的结构。游戏节奏由 **24 处 `SetTimer`** 驱动，
`WM_TIMER` 到达后再由相应的定时器回调推进状态。

**复刻含义**：重制版若采用"回合制函数调用"结构，需要在**行为层**对齐：
定时器的周期、触发顺序、以及同一帧内多个定时器同时到期的先后，
都会影响观察到的行为。这些周期值必须逐个从 `SetTimer` 调用点读出。

### ⚠️ `0x004563f5` 的调用约定（我最初搞错过，特此写明）

实测指令（`VA 0x004563f5`）：

```asm
004563f5  push ebp / mov ebp, esp
004563f8  push dword ptr [ebp + 0x14]    ; 第 5 参
004563fb  push dword ptr [ebp + 0x10]    ; 第 4 参
004563fe  push dword ptr [ebp + 0xc]     ; 第 3 参
00456401  push dword ptr [ebp + 8]       ; 第 2 参   ← ebp+8 是**第 1 个**参数
00456404  push 0x1e0                     ; 480
00456409  push 0x280                     ; 640
0045640e  call 0x455b3a
```

**`[ebp+8]` 是第一个参数**（不是 `[ebp+0xc]`）。我曾在早期分析中把它误读成
「4 个转发参数 + 480 + 640」，据此算出的实参是多了一个的 ——
**凡 `push [ebp+0x14] / [ebp+0x10] / [ebp+0xc] / [ebp+8]` 这种形状，
参数个数以 `ebp+8` 为起点数，不要漏掉 `ebp+8` 本身。**

`0x455b3a` 内部按 `[esi]`(宽) / `[esi+4]`(x) / `[esi+6]`(y) 读一个矩形结构并做裁剪，
故 `0x4563f5` 是「把矩形画到 640×480 表面」的包装。

### PRNG（`VA 0x00456f2d`）—— ✅ 已由原版机器码验证

@source `VA 0x00456f2d` - `0x00456f4f`；设种子函数 `VA 0x00456f50`；
状态块取址 `VA 0x00456f23`（`call [0x488f4c]` + `add eax, 0xc`）。

```asm
00456f2d  call 0x456f23                  ; 取状态块地址 → eax
00456f32  test eax, eax
00456f34  jne  0x456f37
00456f36  ret                             ; 状态块为空 → 直接返回（eax 未定义）
00456f37  imul edx, dword ptr [eax], 0x41c64e6d   ; ★ LCG 乘数
00456f3d  add  edx, 0x3039                        ; ★ LCG 增量
00456f43  mov  dword ptr [eax], edx               ; 写回状态
00456f45  mov  eax, edx
00456f47  shr  eax, 0x10                  ; ★ 取 bit 16..30
00456f4a  and  eax, 0x7fff                ; ★ 15 位结果
00456f4f  ret
```

**完整算法（已确认，不是推测）**：

```
state  = state * 0x41C64E6D + 0x3039      (mod 2^32)
返回值 = (state >> 16) & 0x7FFF           ← 15 位，范围 [0, 32767]
```

⚠️ **易错点**：`0x456f2d` **不只是 LCG**。它还要**取 bit16..30 得 15 位**才返回。
只写 LCG 而直接返回 state，会得到完全不同的随机序列 —— 这是 Mersenne 之外的
经典 `rand()` 形态（`(state>>16)&0x7FFF`），复刻时必须照此实现。

**验证证据**：`tests/test_prng.py` 用 Unicorn 执行原版代码，
5 个种子 × 12 个值 + 状态推进**逐一对齐**，另加 200 次调用的范围检查。

```
陷阱 T-001（必须遵守）：不要沿用 rich4-re 的 asm/mscrt.ld
   它把 _libc_rand 重定向到 msvcrt，随机序列与原版**完全不同**，
   从那个 exe 观测到的任何随机行为都不可信。
```

### 写差分测试时的两个测试台陷阱（踩过，务必避开）

这两条会让"原版行为"看起来完全错误，实则是 harness 自己的问题：

| 陷阱 | 现象 | 正确做法 |
|---|---|---|
| **T-A 补丁被 reset 抹掉** | 打了桩，第二次 `call()` 却跑原逻辑 | 用 `emu.patch()` —— 它会把补丁并入快照 |
| **T-B 状态放在被快照的段里** | 设了种子却没生效，永远从 0 开始 | 状态放 `SCRATCH_BASE`（**故意不纳入快照**的暂存区） |

## 四之二、★★ 落点分派表：**17 种落点类型**（原版"地点/事件"的完整枚举）

> 这是全局最关键的横切结构之一：**玩家移动结束后，按落点类型分派到 17 个处理器之一**。
> 本表由 `跳表 0x004197e9`（17 项）逐项反汇编得到，**每一项都已解出语义**。

### ★ 桩 0（`0x4198b9`）的内部结构：栈帧、三张表与两条「未初始化读」

> 2026-09-18 补。桩 0 是唯一**有实质规则**的落点，内部是一段约 7 KB 的
> 分派阶梯。把它的栈帧与局部槽普查一遍，顺带查出**原版的两处未初始化读**。

#### 栈帧与真正的函数入口

`@source` 本节地址：`VA 0x41982d`、`VA 0x4197e9`、`VA 0x4198b9`、`VA 0x419831`、`VA 0x419837`、`VA 0x419850`、`VA 0x41985b`、`VA 0x4198b2`、`VA 0x498e80`。

桩 0 不是函数入口 —— 全函数的真正入口是 **`0x0041982d`**：

```asm
0041982f  push edi / push ebp
00419831  sub  esp, 0xf8                 ; ★ 帧 0xf8，局部槽到 [esp+0xf4]
00419837  edx = [esp + 0x10c]            ; arg = **节点 id**
0041983e  eax = edx*4 + edx; … = 节点记录（步长 0x28）
00419848  edx = [0x498e80]               ; 节点表
00419850  dx  = [eax + 0x20]             ; ★ 该节点上的「格值」→ [esp+0xf0]
0041985b  ebx = [eax + 0x24] & 0xff      ; 节点占用掩码低字节 → 打**落点类型**
004198b2  jmp dword ptr [ebx*4 + 0x4197e9]   ; 17 项跳表（见上一节）
```

★ **`gen/functions.json` 里 0x4198b9 / 0x41a3be / 0x41abde / 0x41ac3c 都是
这一个函数的「碎片」**（`root: speculative:call-target`，被 `rich4dis.py` 按
call 目标切开）。判据：这些地址的引用**全部来自本函数内部**（自扫
`call|jmp` 指向 `[0x41a3be,0x41b077)` 的 22 处，无一来自函数外），
且它们没有自己的帧（`0x4198b9` 开头就是 `mov ebx,[esp+0xf0]`）。
引用规格里这些碎片地址时请以 `0x41982d` 为准。

  确定值，原版这一支在实测里也从未被观察到「转出非 0 就消失 N 天」。

## 六之二、★ 阻碍状态「消失」的施加与释放（`0x40d375` / `0x40d4e5`）

### 施加：`0x0040d375(player, days, 原因)`

`@source` `VA 0x40d375`（本函数 368 字节 / 120 条，可用 `grep -n '0x40d375' gen/db.txt` 复核）。

```asm
0040d375  push ebx / push esi / push edi / push ebp / sub esp, 4
0040d37c  mov  cl, byte ptr [esp + 0x18]        ; arg1 = 玩家下标
0040d380  mov  edi, 0x100
0040d385  shl  edi, cl                          ; ★ 节点占用掩码 = 0x100 << 下标（bit 8..11）
0040d38b  imul ebx, edx, 0x68                   ; 玩家记录
0040d38e  mov  al, byte ptr [esp + 0x20]        ; arg3 = 原因
0040d392  shl  al, 6                            ; ★ 原因 << 6 → 0x40 位
0040d395  mov  ah, byte ptr [esp + 0x1c]        ; arg2 = 天数
0040d399  or   ah, al
0040d39e  mov  ah, byte ptr [ebx + 0x496b9b]    ; 现有 +0x33
0040d3a4  test ah, ah
0040d3a6  jne  0x40d4c5                         ; ★ 已在消失中 → 累加分支
...
0040d431  add  byte ptr [ebx + 0x496baa], al    ; ★ +0x42 += 天数（首次分支才有）
...
0040d4c5  mov  dl, ah
0040d4c7  and  dl, 0x3f                         ; 旧天数
0040d4d5  add  dh, al
0040d4d7  mov  byte ptr [ebx + 0x496b9b], dh    ; ★ 累加（这里**不**加 +0x42）
```

| 事实 | 值 |
|---|---|
| 计数字节布局 | 低 6 位 = 天数（**不是** 7 位；掩码 `0x3f`）|
| `0x40` 位 | **原因**：0 = 出國觀光，1 = 被外星人綁架（`原因 << 6`）|
| `0x80` 位 | 递减流程挂的「刑满待释放」（见 `rules/blocking.ts`）|
| 调用点 1 | `0x0044c6e0`（`fortune_call_table[6]`，出國觀光）+ `0x0044c7e8` `push 1` 后 `jmp 0x44c6d8`（`fortune_call_table[7]`，外星人綁架）|
| 调用点 2 | `0x0041b05a`（`sub_0041abde`，**航空轉盤**那一支：行业 == 1 且转盘值 ≠ 0 才调用）|

★ `0x40` 位不是死代码：`fortune_call_table[7]` 用 `push 1` + `jmp` 汇入共享尾部
（`0x44c7e8` → `0x44c6d8`），所以「被外星人綁架」确实带这个位。这也解释了
释放时**贴图二选一**（见下）。

### ★ 释放是**两段式**：释放函数只立标记，清账在**走路例程**里（2026-09-18 补）

`@source` `VA 0x41c84f`、`VA 0x41c895`、`VA 0x40d6be`、`VA 0x454fb4`、`VA 0x482414`、`VA 0x40c05c`、`VA 0x40c3ab`、`VA 0x40c3cf`、`VA 0x40c30d`、`VA 0x457dbc`、`VA 0x48baf4`、`VA 0x4749dc`、`VA 0x496b7d`。

```asm

0041c895  test cl, 0x80 / je 递减           ; 刑满挂起位
0041c89b  call 0x40d6be(idx)               ; ★ 共用尾段：住宿/消失/监狱/医院都走它
;   ── 0x0040d6be 全文 39 条，只做三件事 ──
```

要点三条：

1. **清账是「dword 写」** —— 四个阻碍计数一次性清零，不是逐个清；
2. **清账在走路例程里**，条件是 `+0x15 & 0x30` 且 `[0x48baf4] > 0`。
   `[0x48baf4]` 的来历**已查清**（2026-09-18 补）——它 = **这一步的总步数 >> 1**：
   ```asm

   40c249  fild  [esp+0x28]          ; 平方和
   40c24d  call  0x4582bc            ; ★ sqrt（内部 ftst + 0x459c51）
   40c252  fstp  [esp+0xc]           ; = 距离 sqrt(dx²+dy²)（像素）
   40c26d  test  byte [player+0x15], 0x30 / je 0x40c282
   40c27a  fmul  [0x4631dc]          ; 被阻碍/特殊走法：距离 × 0.125（= /8）
   40c290  al = byte [0x4749d8 + (traffic_method & 3)]   ; ★ 步长表 = 8/12/16/8
   40c29e  fdivr [esp+0xc]           ; = 距离 / 步长
   40c2a2  fstp  [esp+0x1c]          ; X = 本趟总步数
   40c304  fld   [esp+0x1c]
   40c308  call  0x457dbc            ; ★ frndint，但先把 CW 舍入模式设成 0x1f = **向零截断**
   40c30d  fistp [0x4749dc]
   40c313  eax = [0x4749dc] / sar eax,1 / [0x48baf4] = eax
   ```
   ⇒ 清账条件 `[0x48baf4] > 0` ⟺ **`trunc(距离 / 步长) >= 2`**。
   骰子走一格约 24 px、步长 8 → `3` ⇒ 照常清；只有「**距离 < 2×步长**」的极短走法
   （例如两格挨得近）才会跳过清账。
3. `+0x15` 的 `0x30` 是**两个**标记：`0x10` → 清四个计数；另一支（只带 `0x20`）走

   **2026-09-19 已由通道 2 结案**，见下面 §「走路例程已整段差分」。
