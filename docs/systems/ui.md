# UI 界面（UI Screens & Interaction）

> 真值：`../../Rich4/rich4.exe`。本文件的**结构部分**（界面清单、模态界面、输入架构、
> 刷新模型）由 `tools/` 从 exe 直接抽取，**可复核**；
> **像素布局与观感**无法从反汇编判定，见 §六。
>
> 与 `render-api.md` 的分工：那边讲**对外 API 与渲染链路**，本文件讲**界面与交互**。

## 一、输入架构（**与原版同时代游戏很不一样，必须照做**）

| 输入 | 机制 | 证据 |
|---|---|---|
| **键盘** | **全局钩子 `WH_KEYBOARD`**，回调 `VA 0x00401010` | `SetWindowsHookExA(2, 0x401010, hInstance, 0)` @ `VA 0x0040178b` |
| **鼠标** | **`GetCursorPos` 轮询**（7 处），每个界面自己查光标位置 | `render-api.md` §五 |
| 窗口消息 | `WndProc`（`0x4019dd`）只处理 `WM_DESTROY`、`WM_ACTIVATEAPP`、自定义 `0x3b9` | `game-loop.md` §二 |

### 钩子与窗口激活的联动（一处易漏的细节）

```asm
0040101f  cmp  byte ptr [0x46cb01], 0   ; ★ 窗口是否激活
00401026  je   0x401537                 ; 未激活 → 整个钩子直接返回
```

而 `[0x46cb01]` 正是 `WndProc` 在 `WM_ACTIVATEAPP` 里置位的（`game-loop.md` §二：
`00401a93  mov byte ptr [0x46cb01], 1`）。

**复刻含义**：键盘在窗口失焦时必须**完全无效**（不是"忽略但消费"）。
现代框架的默认行为通常是"失焦后仍收到部分事件"，需要显式加上这道闸门。

钩子还把按键与 `[0x497168]` 比较（`00401038  mov ax, word ptr [0x497168]`），
该全局与 `RICH4.CFG` 的按键配置同区 —— **按键可被玩家重定义**。

## 一之二、★ 窗口与消息架构（**与常见 Win32 程序很不一样**）

### 游戏只有**一个窗口**

| API | 调用点数 | 结论 |
|---|---|---|
| `RegisterClassA` | **1 处**（`VA 0x00401c08`；另有 1 处是导入 thunk） | 只注册**一个窗口类** |
| `CreateWindowExA` | **1 处**（`VA 0x00401c44`；另有 1 处是导入 thunk） | 只创建**一个窗口** |

**推论（重要）**：所有"界面"**不是独立窗口**。它们是**画在同一块表面上**、
各自跑一段消息循环的**模态过程**。复刻**不能给每个界面建一个窗口** ——
那会引入原版没有的窗口管理、焦点、Z 序与重绘语义。

### 消息如何路由到"当前界面"

`WndProc`（`0x4019dd`）只显式处理 3 种消息（`WM_DESTROY`、`WM_ACTIVATEAPP`、
自定义 `0x3b9`）。**其余全部消息**走默认分支，在那里做**转发**：

```asm
00401b33  mov  ebx, dword ptr [0x46cad8]        ; ① 模态嵌套深度
00401b39  shl  ebx, 2                            ;   ×4（指针数组下标）
00401b3c  cmp  dword ptr [ebx + 0x48a010], 0    ; ② 当前界面的消息处理器
00401b43  je   0x401b59
00401b45  mov  edi, dword ptr [esp + 0x20]
00401b49  push edi / push edx / push eax / push ebp
00401b51  call dword ptr [ebx + 0x48a010]        ; ★ 转交给界面处理器
00401b57  jmp  0x401b6c
00401b59  … call DefWindowProcA                  ;   无处理器 → 默认处理
```

**注册点**：`modal_msg_pump`（`0x4018e7`）把它的**第 1 个参数**写进
`0x48a010[深度]`（`VA 0x004018fe`）：

```asm
004018fa  mov  edx, dword ptr [esp + 0x24]      ; ★ 第 1 参 = 界面处理器
004018fe  mov  dword ptr [eax*4 + 0x48a010], edx
```

于是：
```
modal_msg_pump(handler_fn, …)
    → 0x48a010[depth] = handler_fn
    → 跑消息循环；未识别的消息经 WndProc 转发给 handler_fn
    → 退出时 depth-- （0x401957）
```

**这就是原版的"对话框过程"**：不是 Win32 对话框，而是
**"把函数指针压进一张按深度索引的数组"**。

另有 1 处**硬编码注册**：`VA 0x0040198f`
`mov dword ptr [edx*4 + 0x48a010], 0x417e26`（把總資產面板注册为处理器）。

### 复刻要点（这一节的直接结论）

1. **单窗口**：不要给每个界面建窗口。
2. **消息按模态深度路由**：`0x48a010[depth]`，深度由 `0x46cad8` 维护。
   嵌套时深层覆盖浅层，退出时 `depth--` 自动回退。
3. **界面的消息处理器是裸函数指针**，签名与 WndProc 同形
   （`(hwnd, msg, wParam, lParam)`，见 `0x401b45`–`0x401b50` 的 4 次 push）。
4. **未注册处理器时回落到 `DefWindowProcA`** —— 复刻需保留这条回落。

### §1.1 ★ 机械复算：**42 处注册、46 个处理器**（2026-09-16 订正）

上一节的「42 个处理器」是**按 `call 0x4018e7` 的出现次数**数的。
沿控制流复算后发现它**少数了 4 个** —— 有注册点是**多条跳转汇入共享**的：

```asm
004283c2  push 0
004283c4  push 0x42608f        ; ★ 处理器已压栈
004283c9  jmp  0x42839c        ;   但 call 不在这里，而在 0x42839c
...
00428397  push 0x4258c1        ; 另一条路径压的是别的处理器
0042839c  call 0x4018e7        ; ← 共享的注册调用
```

⇒ 全 exe `call 0x4018e7` **42 处**，实际注册的处理器是 **46 个**。
复算脚本（沿前驱回溯收集 `push` 立即数，能跟 `jmp` 汇入）：

```bash
python3 tools/scratch/list_ui_handlers.py
```

（宿主 `0x427c21` 的子状态机按 `[0x48c2ca]` 分派，

## 三之二、★ 控件与 hit-test 机制（A 级）

### 唯一的 hit-test 辅助函数：`VA 0x004174cd`（10 处调用）

```asm
004174d1  cmp  byte ptr [0x46cafd], 0        ; 某个"允许交互"开关
004174d8  je   0x417530                       ; 关 → 直接返回 0
004174da  mov  eax, dword ptr [0x475284]      ; ★ 光标 x
004174e3  mov  eax, dword ptr [0x475288]      ; ★ 光标 y
004174f0  mov  edx, dword ptr [0x48bdd8]      ; ★ 当前区域 宽
004174f8  …                                    ; rect.left/top  = 光标坐标
00417506  mov  ecx, dword ptr [0x48bddc]      ; ★ 当前区域 高
0041750c  mov  ebx, dword ptr [esp + 0x28]    ; 第 1 参 = 待测矩形
0041751b  call dword ptr cs:[0x4622f4]        ; ★ USER32!IntersectRect
00417522  test eax, eax
00417524  je   0x417530
```

**语义**：`hit_test(RECT *r) -> bool` —— 把**光标点**当成一个 1×1（或 w×h）矩形，
与传入的矩形求交。**全程只用 `IntersectRect`，没有手写的边界比较。**

### 相关全局

| 全局 | 语义 | 写入点 |
|---|---|---|
| `0x475284` | **光标 x** | 3 处（`0x418aa8`…`0x418ad3` 区） |
| `0x475288` | **光标 y** | 3 处（`0x418aae`…`0x418b00` 区） |
| `0x48bdd8` | **当前 hit 区域 宽** | **1 处**（`0x4180ca`） |
| `0x48bddc` | **当前 hit 区域 高** | **1 处**（`0x4180d4`） |
| `0x48be04` | **指向当前 UI 元素记录** | **1 处**（`0x41915b`） |
| `0x475110` | **当前元素的交互状态位** | 多处（bit0 / bit1） |

### 区域宽高的来源：UI 元素记录

```asm
004180c1  mov  eax, dword ptr [0x48be04]   ; ★ 当前 UI 元素记录
004180c6  movsx edx, word ptr [eax + 0xc]  ; ★ 元素 宽（int16）
004180ca  mov  dword ptr [0x48bdd8], edx
004180d0  movsx eax, word ptr [eax + 0xe]  ; ★ 元素 高（int16）
004180d4  mov  dword ptr [0x48bddc], eax
```

⇒ **UI 元素记录至少有 `+0xc`（int16 宽）与 `+0xe`（int16 高）**。
`[0x48be04]` 在**运行时装表**（`.bss`，文件中无初值）。

### 典型调用序列（以 `VA 0x00419380` 为例）

```asm
00419385  call 0x40235d                 ; 取/准备元素
004193a5  call dword ptr [edx + 0x1c]   ; ★ 绘制该元素（表面 blit）
004193ab  call 0x4174cd                 ; ★ hit_test
004193b6  call 0x402250                 ; 后续辅助（状态更新？）
004193be  mov  dh, byte ptr [0x475110]  ; ★ 读元素状态位
004193c4  test dh, 2                    ;   bit1
004193c7  je   0x41942f                 ;   未置位 → 走另一分支
```

**即固定三步：绘制 → `hit_test` → 按状态位分支。**
这就是原版"控件"的实现方式 —— **不是子窗口、不是控件库，而是
"逐元素绘制 + 逐个矩形求交 + 一个状态字"**。

### 复刻要点

1. `hit_test` **只做矩形求交**（`IntersectRect`），没有手写边界比较。
   复刻用等价的矩形包含判断即可，但要保证**含边界**（`IntersectRect`
   对相邻/相接矩形的行为）一致。
2. 区域宽高来自**元素记录的 `+0xc`/`+0xe`（int16）** —— 复刻的控件
   记录要保留这两个字段的位置语义（**但 `+0x0`..`+0xb` 的布局未解析**）。
3. 光标位置是**全局缓存**（`0x475284/0x475288`），由轮询更新，
   不是每次 `hit_test` 现查。

### 未决

- **`0x475110` 的位语义未确证**：已知 bit0、bit1 存在，且 `0x4193c4`
  在读 bit1 后分支。本轮尝试用"调用点前后 20 字节"读原始指令时
  **遇到错位解码**（见 §七 未决 2 的同类问题），故**未下结论**。
  要确证需按**函数边界**（而非裸字节窗口）反汇编那两个置位点。
- **UI 元素记录的完整布局**（`+0x0`..+0xb、`+0x10` 之后）未解析。
- **元素表的位置与项数**未确定（`0x48be04` 是"当前"指针，表在哪里未追）。

## 三之三、★ 界面导航图：**42 条边**（A 级）

### 边的定义

原版的"打开一个界面" = **调用 `modal_msg_pump(handler, arg)`**。
所以导航图的边就是 **`(打开者函数 → 界面处理器)`** 这一对，
可以从 42 个 `modal_msg_pump` 调用点**机械提取**（第 1 参 = 处理器）。

### `modal_msg_pump` 的三步（`VA 0x004018e7`）

```asm
004018fa  mov  edx, dword ptr [esp + 0x24]
004018fe  mov  dword ptr [eax*4 + 0x48a010], edx   ; ① 注册处理器（按深度）
00401905  mov  ecx, dword ptr [esp + 0x28]
0040190c  push 0x401 / mov ebx,[0x48a0d4] / push ebx
00401918  call dword ptr cs:[0x462310]              ; ② ★ PostMessageA(hwnd, 0x401, 0, arg)
0040191f  …  PeekMessageA 循环                        ; ③ 跑消息循环
00401957  dec  dword ptr [0x46cad8]                 ; ④ 退出时深度--
```

**★ 这就是 `0x401` 的来历**：**消息泵自己投递 `0x401`（`WM_USER+1`）**
用来通知刚打开的界面"**重绘自己**"。这解释了为什么 `0x401`
在 **51 个函数**里被处理 —— 每个模态界面都要响应它。

### 界面处理器实现的**消息阶梯**（以 `0x40257a` 为例，`VA 0x00402581`）

```asm
00402581  mov  eax, dword ptr [esp + 0x70]   ; msg
00402589  cmp  eax, 0x200                     ; WM_MOUSEMOVE
00402590  jbe  0x402762
00402596  cmp  eax, 0x201                     ; WM_LBUTTONDOWN
0040259b  jbe  0x402620
004025a1  cmp  eax, 0x401                     ; ★ WM_USER+1（重绘）
004025a6  je   0x4025bb
004025ad  cmp  eax, 0xf                       ; WM_PAINT
004025b0  je   0x402989
004025a8  jmp  0x4029e5                       ; 其它
```

`0x401` 的处理体（`VA 0x004025bb`）：**重置选中索引 → 重画背景**：

```asm
004025bb  mov  dword ptr [0x48a184], -1      ; ★ 选中索引 = 无
004025d8  call dword ptr [edx + 0x64]        ; 表面操作
004025ef  call 0x4563f5                      ; ★ blitRect（画背景）
```

> 注意：模态界面**同时**处理 `WM_MOUSEMOVE`/`WM_LBUTTONDOWN`（消息驱动），
> 与 §一 说的"鼠标靠 `GetCursorPos` 轮询"**并存** ——
> 轮询用于棋盘等**非模态**场景，模态界面则收转发来的鼠标消息。

### "返回"是怎么实现的

**不需要显式返回消息**：界面处理器跑完自己的逻辑后**从 `modal_msg_pump` 返回**，
泵在退出时执行 `dec dword ptr [0x46cad8]`（`VA 0x00401957`）——
**深度减一，上一层界面的处理器自动重新成为当前处理器**。
即**导航栈由 `0x46cad8` 这个整数维护**，没有显式的栈结构。

### 复刻要点

1. **打开界面 = 注册处理器 + 投递 `0x401` + 跑循环**；关闭 = 函数返回（深度自减）。
2. **`0x401` 必须实现**（重绘），否则新打开的界面不会画出来。
3. 界面处理器要实现 `0x200`/`0x201`/`0x401`/`0xf` 的消息阶梯。
4. **深度是整数，不是栈** —— 复刻用一个计数 + 数组即可，但要保证
   "深层覆盖浅层、退出自动回退"的语义。

## 四、刷新模型：`WM_PAINT` 局部重绘

| API | 调用点数 | 出现在多少个函数 |
|---|---|---|
| **`InvalidateRect`** | **204** | **124** |
| `BeginPaint` / `EndPaint` | 各 41 | 各 41 |
| `ValidateRect` | 7 | 7 |

**含义**：每个界面自行声明**失效区域**，等 `WM_PAINT` 重画该区域。
`InvalidateRect` 高度分散（124 个函数）说明这是**逐界面的约定**，不是集中式重绘管理。

**复刻要点**：不要改成整屏重绘 —— 会在闪烁、遮挡顺序、
以及「點哪兒都退屏」这类交互细节上偏离。

## 五、文字与语音控制码

所有文字走 `drawText_colorcode`（`VA 0x0044fabc`，被调 **86 次**）：
`SelectObject` → `SetBkMode` → `SetTextCharacterExtra` → `DrawTextA` → `SetTextColor`。

其中 `#NNNN`（`VA 0x0044fb00`）是**语音控制码**：
取 4 位十进制 → `call 0x45441a`（`play_speech`）→ `add ebx,5` 跳过前缀。

> ⚠️ 本项目早期把 `#NNNN` 写成"颜色码"，**是错的**；
> 颜色来自全局（如 `0x4762e4`）。详见 `dialogue-voice.md` §三。

**复刻要点**：`#NNNN` 必须**既播语音、又从显示文本中剥离**。

## 八、复刻要点

1. **键盘走全局钩子，且失焦时整段失效**（`[0x46cb01]` 闸门）。
2. **鼠标用 `GetCursorPos` 轮询**，不是事件驱动 —— 复刻若改成 `mousemove` 事件，
   采样时机与原版不同，快速拖动时的手感会变。
3. **模态界面有嵌套语义**（深度 + 层级过滤器），不可简化为"弹一个对话框"。
4. **局部重绘**（124 个函数各自 `InvalidateRect`），不是整屏重绘。
5. **`#NNNN` 语音控制码要剥离**，否则 UI 会显示 `#0428` 这种数字。
6. 土地資訊標註在 7 处内联重复 —— 复刻应抽成共用函数，但要**逐处核对其差异**
   （目前未逐处比对，见 §七）。
