# AI 决策

> 真值：`Rich4/rich4.exe`（ImageBase `0x400000`，PE32，v3.11）。
> 所有 `@source` 均为原版虚拟地址。本文件凡「未决」处**不给推测值**。

## 本文件的验证方式与证据级别

| 级别 | 含义 | 本文中的例子 |
|---|---|---|
| **A（机器可复核）** | 反汇编指令本身；任何人在同一 exe 上重跑即得同样字节 | 個性闸门 `0x41e69e`；`_rich4_find_most_hostile_player` `0x40d2d3`；行动路由跳表 `0x417d39` |

| **C（未决）** | 无法从 exe 断言 | 各 case 内的完整判据、股票/银行 AI 的阈值 |

## 一、AI 决策的整体结构

### 1.1 决策时机与调用者：**没有独立的 AI 主循环**

原版**不存在**「轮到 AI → 跑一个 AI 函数」的结构。
AI 的决策点**嵌在落点结算与行动总线的同一条通路里**，
由回合状态机在**当前玩家是电脑**时进入（真人则走 UI 分支）。

### 1.2 顶层结构：主循环 → `0x418c55` → **相位跳表 `0x418c3d`**

**顶层是主循环每帧一次**：WinMain 段（`0x401b9e` 起）在 `0x401bb0` 登记窗口过程
`0x4019dd`，`0x401d38` / `0x401d5f` 是 `PeekMessageA` / `DispatchMessageA`。
消息泵每帧之后进入「决策点」：

```asm
00401d8d  imul     eax, dword ptr [0x49910c], 0x34
00401d94  cmp      byte ptr [eax + 0x498ea2], 0
00401d9b  jne      0x401db8
00401d9d  mov      ch, byte ptr [eax + 0x498ea0]
00401da3  test     ch, 0x80                  ; ★「该玩家有待处理决策」标记
00401da6  je       0x401db8
00401dad  mov      byte ptr [eax + 0x498ea0], dl
00401db3  call     0x418c55                  ; ★ 回合决策驱动（唯一调用点）
```

**`0x418c55` = 回合决策驱动**，内部按当前玩家所处「相位」分派：

```asm
00418d6e  push     0
00418d70  call     0x40c912          ; 取相位 → eax ∈ 0..5
00418d78  cmp      eax, 5
00418d7b  ja       0x418e7a
00418d81  jmp      dword ptr [eax*4 + 0x418c3d]   ; ★★ 6 项相位跳表
```

**相位跳表 `0x00418c3d`（6 项，逐 dword 读出）**：

| 相位 | 入口 | 实际代码 | 归类 |
|---|---|---|---|
| 0 | `0x00418d88` | `call 0x418e7f`；`mov byte [0x46cafb],1`；`ret` | **落点事件结算**（含小游戏，见 `small-games.md`） |
| 1 | `0x00418d99` | `call 0x4196f1`；`SetCursorPos`；`push 1; call 0x402460` | 光标/画面复位 |
| **2** | `0x00418dc6` | 见 §1.3b | ★ **AI 决策块** |
| 3 | `0x00418e7a` | 直接收尾 | 空 |
| 4 | `0x00418e7a` | 直接收尾 | 空 |
| **5** | `0x00418dc6` | 同相位 2 | ★ **AI 决策块（同一段代码）** |

**AI 决策块 `0x00418dc6` 的完整顺序**：

```asm
00418dc6  mov      esi, dword ptr [0x49910c]
00418dcc  cmp      esi, 4
00418dcf  jge      0x418e75                  ; current_player >= 4 → 不决策
00418dd5  imul     eax, esi, 0x68
00418dd8  test     byte ptr [eax + 0x496b7d], 0x30   ; ★ 玩家+0x15 的 bit4/bit5
00418ddf  jne      0x418e75                  ; 有该标志 → 不决策（卧病/坐牢等）
00418de5  push     esi / call 0x42bf03      ; 三步前置（准备）
00418df4  call     0x42c79f
00418dfe  call     0x436b0a
00418e06  cmp      byte ptr [0x46caf8], 0
00418e0d  jne      0x418e7a
00418e13  call     0x4284be                  ; （与路由 case 9 同一函数）
00418e18  call     0x456f2d                  ; ★★★ 硬币
```

### 1.2b 落点事件相位 `0x00418e7f`

```asm
00418e7f  push     1
00418e81  call     0x40c912          ; 取落点事件
00418e89  test     eax, eax
00418e8b  je       0x418ead
00418e8d  imul     eax, dword ptr [0x49910c], 0x68
00418e94  mov      ax, word ptr [eax + 0x496b74]   ; 玩家 +0x0c = node_id
00418ea0  push     eax
00418ea1  call     0x41982d           ; ★ 落点结算分派（含买地/盖房/小游戏）
```

- 调用者：`0x0040d889`、`0x00418d88`（后者位于
  `0x418d6e` 的 `jmp [state*4 + 0x418c3d]` 的 state=0 分支）。
- `0x41982d` 按「落点类型」（`[0x498e80 + node_id*0x28 + 0x24]`，低字节）
  走跳表 `0x4197e9`（17 项）。**买地/盖房/用卡/用道具都在这张表的 case 里**
  或由它调用的子函数里完成。

### 1.3 行动路由 `0x00417d65`：AI 的「做哪一类事」

00417d68  call     0x402460
00417d70  call     0x419703           ; 清屏/刷新
00417d75  mov      dword ptr [0x48bde4], 0xffffffff
00417d7f  push     1
00417d81  call     0x415d31           ; 参数 1
00417d89  mov      ecx, dword ptr [esp + 8]   ; ★ 参数 = action
00417d8d  cmp      ecx, 0xa
00417d90  ja       0x417dff
00417d96  mov      eax, ecx
00417d98  jmp      dword ptr [eax*4 + 0x417d39]   ; ★★ 行动跳表（11 项）

**跳表 `0x00417d39`（11 项，逐项读出）**：

|---|---|---|---|

case 0..6 与 10 都是系统窗或资讯窗。每个 case 内的**具体判据**仍逐条标「未决」。

### 1.3b ★★ 用卡 vs 用道具：**一次 50/50 硬币**（不是优先级）

`0x447d97`（case 7）与 `0x441baa`（case 8）**不都由路由触发**。
真正的分派在 `0x00418dfe` 一带，且**每回合只跑一个**：

```asm
00418dfe  call     0x436b0a          ; 回合内某步骤
00418e03  add      esp, 4
00418e06  cmp      byte ptr [0x46caf8], 0
00418e0d  jne      0x418e7a
00418e13  call     0x4284be          ; （与路由 case 9 同一个函数）
00418e18  call     0x456f2d          ; ★★★ _libc_rand
00418e1d  test     al, 1             ; ★ 只取最低位
00418e1f  je       0x418e28
00418e21  call     0x441baa          ; 奇数 → **用卡**
00418e26  jmp      0x418e2d
00418e28  call     0x447d97          ; 偶数 → **用道具**
```

**⇒ 判定 = `rand() & 1`，即 50/50，每回合一次，二选一。**
这是一处**此前未被任何记录覆盖的 AI 随机消耗点**，1:1 复刻必须保留。

### 1.4 谁调用路由、action 从哪来

`tools/r4scan.py 0x417d65` 只有两个调用点：

| 调用点 | 来源 | 传入 action | 证据 |
|---|---|---|---|
| `0x00401321` | **全局键盘钩子 `0x401010`**（`SetWindowsHookExA(WH_KEYBOARD)` 安装于 `0x40178b`，IAT `0x462328`） | 来自 **WORD 表 `0x497168`（28 项，stride 2）**，由缺省表 `0x47edc2` 经 `0x456de8` memcpy 或 `RICH4.CFG`（`0x411f80` fread `0x38`）填充 | `0040131f push 0xa`（键表里映射到 action 10 的那一项） |
| `0x00418870` | **棋盘屏处理函数 `0x417e26`** 的 `WM_LBUTTONUP(0x202)` 分支 | `bl = [0x48be28]`；`bl >= 0x64` 时 `action = bl - 0x64` | `00418863 cmp bl,0x64` / `0041886c sub eax,0x64` / `00418870 call 0x417d65` |

**这些 action 是「玩家点出来的」**：键盘钩子里 `esi = [esp+0x20]` 是 VK 键码，
工具条的格号在 `WM_LBUTTONDOWN` 分支写入（`0x418670 cmp esi,0x1b8` /
`0x418678 cmp edx,0x28` / `0x418698 idiv 0x28` / `0x41869a add eax,0x64`）
⇒ 即**左上角 440×40 的 11 格横向工具条**（每格 40 px），
格号 = `x/40 + 0x64`。

> ⚠️ **`0x417d65` 与 AI 自动决策不是同一条路**：它由**玩家的键盘/鼠标**触发，
> 是「玩家选择要做哪一类事」的执行入口。证据：两个调用点一个在
> 全局键盘钩子、一个在棋盘屏的 `WM_LBUTTONUP`；且 case 9 的 `0x4284be`
> 开头就是 `0x4284d1 cmp byte ptr [eax+0x496b7d], 1 / jne 0x42886e`
> —— **非电脑才走 UI 面板**，说明它是给玩家用的。
>
> 真正的 **AI 自动决策**走相位 2/5 的 `0x418dc6`（见 §1.2 与 §1.3b）：
> 以 `rand()&1` 决定用卡还是用道具，**不经过 `0x417d65`**。
> `0x418e13` 调用的 `0x4284be` 是那个函数里 `jne 0x42886e` 指向的**电脑分支**
> ⇒ 同一个函数被「玩家点工具条的股市按钮」和「AI 决策块」两处复用，
> 只是进入后按 `+0x15` 分成 UI / AI 两支。

## 二、個性闸门 `0x0041e69e`（**原版含真实随机**）

```asm
0041e69e  mov      eax, dword ptr [esp + 4]          ; action
0041e6a2  xor      edx, edx
0041e6a4  mov      dl, byte ptr [eax*8 + 0x47fdf1]   ; ★ 该行为的「所需個性」
0041e6ab  imul     eax, dword ptr [0x49910c], 0x68
0041e6b2  mov      al, byte ptr [eax + 0x496b7f]     ; ★ 當前玩家 +0x17 = 個性
0041e6b8  and      eax, 0xff
0041e6bd  sub      edx, eax                          ; edx = 所需 - 自己
0041e6bf  mov      eax, edx
0041e6c1  cmp      edx, 2
0041e6c4  jl       0x41e6c9
0041e6c6  xor      eax, edx                          ; edx>=2 → eax=0（从不做）
0041e6c8  ret
0041e6c9  cmp      edx, 1
0041e6cc  jne      0x41e6e6
0041e6ce  call     0x456f2d                          ; ★★ _libc_rand
0041e6d3  mov      edx, eax
0041e6d5  mov      ecx, 3
0041e6da  sar      edx, 0x1f
0041e6dd  idiv     ecx                               ; edx = rand() % 3
0041e6df  test     edx, edx
0041e6e1  je       0x41e6e6                          ; ★ 余数 == 0 → 做
0041e6e3  xor      eax, eax
0041e6e5  ret                                         ; 余数 != 0 → 不做
0041e6e6  mov      eax, dword ptr [esp + 4]
0041e6ea  call     dword ptr [eax*4 + 0x475324]      ; 行为跳表
0041e6f1  ret
```

### 判据（A 级）

```
d = card_table[action].f7 - player[current].personality      ; 0x496b7f = 玩家+0x17
if (d >= 2)  return 0;                    // 从不做
if (d == 1)  { if (rand() % 3 != 0) return 0; }   // ★★ 1/3 概率做，消耗一次 rand()
return action_table[action]();            // 照做
```

| 项 | 值 | 地址 |
|---|---|---|
| 所需個性字节 | `0x47fdf1 + action*8` | **立即数地址**（`card_table + 7`） |
| 玩家個性字节 | `0x496b7f` = 玩家基址 `0x496b68` + `0x17` | |
| 個性取值 | 0 乖寶寶 / 1 普通人 / 2 大老奸 | 写者 `0x0041ed3e`、`0x0041f6bf`（B 级） |
| **`rand() % 3` 调用点** | **`0x0041e6ce`**，除法 `0x0041e6dd`，比较 `0x0041e6df` | **★ 1:1 复刻必须保留此调用** |

### ★ 与既有偏差记录 D-004 的关系（纠正）

`rich4-remake/docs/known-deviations.md` 的 D-004 写的是：
> 原版 `0x0041e6c9` 那次 `rand() % 3` 消耗全局随机序列。

**精确化**（本次反汇编确认）：

1. `0x41e6c9` 是 `cmp edx,1 / jne`，`rand()` 调用点实际在 **`0x0041e6ce`**。
   原记录把分支标签当成了调用点——不影响行为描述，但地址应订正。
2. 语义是 **`rand() % 3 != 0` → 不做**，即**恰好 1/3 概率做**。
   重制版用「1/3 的确定性替身」在**分布**上对齐，但
   **不消耗** `rand()` 序列这一点与原版不同：原版这次调用**推进 LCG 状态**
   （`0x456f2d` 内部写回 `state`），后续所有随机事件都会因此错位。
3. 因此 1:1 复刻的正确做法是：AI 每次过闸门且 `d == 1` 时，
   **按 `0x456f2d` 的完整算法掷一次**（见 `game-loop.md` 的 PRNG 规格：
   `state = state*0x41C64E6D + 0x3039; return (state>>16) & 0x7FFF`），
   再判 `% 3`。**不能**用状态派生替身。

### 3.3 AI 用卡判据（A 级）

```
前置闸门 1   = (玩家+0x15 & 6) != 0                             （0x441d00）
前置闸门 2   = (玩家+0x16 & 1) != 0                             （0x441d09）
手牌槽       = byte [0x499120 + player*15 + i]    i = 0..14        （0 = 空）
手牌数 N     = 0x441262(player)                                    （上界 0xf）
候选数上限   = 8（循环 0x441d61 cmp ebx,8 / jge）
起点 s       = (N > 8) ? rand() % N : 0            （0x441d4a / 0x441d50）
候选 k=0..7  = 槽[(s + k) % N]
对每个候选 c（跳过 0）：
    if (0x41e69e(c) != 1) continue;                 // 個性闸门
    打印卡名; 0x441f73(player, c);                   // 提交
    0x475d5c[c]();                                   // 执行效果
    return;
```

**要点**：

1. **AI 只看前 8 个候选**（`cmp ebx, 8` 于 `0x441d61`）——即使有 15 张牌，
   也只有随机起点起的 8 张有机会被选中。
2. **起点随机**：只在 `N > 8` 时掷 `rand() % N`（`0x441d4a`→`0x441d50`）。
   `N <= 8` 时**不掷**（`xor esi,esi`），起点恒为 0。
   ⇒ **这是一处极易漏掉的随机消耗点**，1:1 复刻必须保留。
3. **两张跳表用途不同**：
   - `0x475324[action]` = 個性闸门通过后的**「照做」入口**（`0x41e6ea`）；
   - `0x475d5c[action]` = **卡片效果表**（`0x441e00`）。
     二者**按同一个 action 下标并行**（1 基：卡 1..30 / 道具 31..43）。
     证据是两者的**桩位完全对应**：`0x475324` 的索引 `5,6,18,19,20,21`
     都指向 `0x41e6e3`（`xor eax,eax; ret`），而 `0x475d5c` 的同 6 个索引
     都指向 `0x4420d5`（空实现）；另 `0x4420d5` 也是 `0x475d5c` 索引
     `18..21` 的值。（逐项读出 `0x475324+action*4` 与 `0x475d5c+action*4`。）
4. `0x41e69e` 通过后 `0x441f73` 是**提交/动画**（参数 `(player, card)`，
   第二个参数经 `esp` 传递，见 `0x441de7`/`0x441dee`）。

> `0x41e6f2(index)` / `0x420eee(index)` 读回。
> ⇒ **决策与执行是两段、经全局暂存池解耦**，复刻时必须保留此时序。

#### 3.4b ★★ `0x41e8e6`：「这块产业值得从对手手里拿吗」`[A]`

### 3.5b 逐卡判据（action 1..30）—— 状态与已知样例

**逐卡判据的完整表**由子代理产出在 `.work/ai_cards.md`（约 48 KB，逐卡附 VA + 逐字汇编），
本文件只收录**已复核的通用结构与样例**，避免转述失真。

已复核的**通用事实**：

1. **地图格表 `0x48b8c4`**：word 数组，长度 **`0x1b8` = 440**
   （`push -1; call 0x40a45c` 返回该长度）。取值约定（A 级）：
   - `0x7d0 < w < 0xfa0` → **住宅**地块，索引 `w − 0x7d0`，步长 `0x34`，基址 `[0x498e84]`；
   - `0xfa0 < w < 0x1770` → **商業**地块，索引 `w − 0xfa0`，步长 `0x38`，基址 `[0x498e88]`；
   - 其余且 **bit15 置位** → 「地图物件」编码（`0x441f6a9` 拆除卡用到）。
2. **地产记录的「地名」是记录内联的 Big5 字符数组（在 `+4`），不是指针**。
   证据：`0x419abc lea eax, [esi + 4]` 把 `rec+4` 直接推给
   `_rich4_calculate_land_toll`（其第二参是 `const char*`，见 `land-rent.md`），
   而 `0x419744` 内部对该实参用 `strcmp`（`0x419787 call 0x458370`）；
   同理 `0x41f0e0` 附近把两条记录的 `+4` 直接推给 `0x458370`。
   `0x458370` 的实现（`0x458375 mov edx,[esp+0xc]` 后 `0x458381 mov eax,[ebx]`）
   是把**实参本身**当字符缓冲读，所以 `+4` 处必须是字符数据。
   ⇒ `BRIEF.md` 写的「+4 = 地名指针」**表述不准**（`+4` 是字符数组首地址）。
   ⚠️ 这也意味着**不能**把 `[rec+4]` 当 dword 解引用成“名字指针”。
3. **拥有者是 1 基**（`+0x19`，0 = 无主）；比較时用 `current_player + 1`。
4. 每张卡都有**自己的 `rand()`**（用于在多个候选街道/地块中挑一个）——
   见 §五 #18 与 `.work/grp1.md` / `grp4.md` 的 `rand()%n` 记录。

## 四、`_rich4_find_most_hostile_player` 精确算法

**VA `0x0040d2d3`**（不是 `0x40d2b4`——后者是「数电脑玩家数」）。

```asm
0040d2d3  push     ebx
0040d2d4  push     esi
0040d2d5  push     edi
0040d2d6  mov      esi, dword ptr [esp + 0x10]   ; ★ 参数 = 自己的玩家下标
0040d2da  xor      eax, eax                       ; i = 0
0040d2dc  xor      ecx, ecx                       ; best = 0
0040d2de  mov      edi, 0xffffffff               ; bestIdx = -1
0040d2e3  cmp      eax, dword ptr [0x499114]      ; num_players
0040d2e9  jge      0x40d316
0040d2eb  cmp      eax, esi
0040d2ed  je       0x40d313                       ; ★ 跳过自己
0040d2ef  imul     edx, eax, 0x68
0040d2f2  cmp      byte ptr [edx + 0x496b7d], 0   ; ★ 跳过 who_plays==0（出局/未参与）
0040d2f9  je       0x40d313
0040d2fb  imul     edx, esi, 0x68                 ; edx = 自己 * 0x68
0040d2fe  mov      ebx, eax
0040d300  shl      ebx, 2                         ; ebx = i * 4
0040d303  add      edx, ebx
0040d305  mov      ebx, dword ptr [edx + 0x496bb4]  ; ★ 自己.hostility[i]
0040d30b  cmp      ecx, ebx
0040d30d  jge      0x40d313                       ; ★★ best >= h → 不更新（tie-break）
0040d30f  mov      ecx, ebx                       ; best = h
0040d311  mov      edi, eax                       ; bestIdx = i
0040d313  inc      eax
0040d314  jmp      0x40d2e3
0040d316  mov      eax, edi                       ; ★ 返回 bestIdx
0040d318  pop      edi / esi / ebx
0040d31b  ret
```

### 算法（A 级）

```c
int find_most_hostile_player(int self) {           // 0x0040d2d3
    int best = 0, bestIdx = -1;
    for (int i = 0; i < num_players /*0x499114*/; i++) {
        if (i == self) continue;
        if (player[i].who_plays /*+0x15*/ == 0) continue;
        int h = player[self].hostility[i];          // 0x496bb4 + self*0x68 + i*4
        if (best >= h) continue;                    // ★ jge → 严格大于才更新
        best = h; bestIdx = i;
    }
    return bestIdx;                                 // 全 0 / 无人可比 → -1
}
```

### tie-break 规则

`0x40d30d` 是 **`jge`**（`cmp ecx, ebx` 后 `jge`）。
⇒ 只有**严格大于**当前最大值才更新 `bestIdx`；
**敌意相同者，下标小的先占位并保持**（first-wins）。
例：`hostility = [5, 5, 3, 0]` → 返回 **0**（不是 1）。
全部为 0 时返回 **-1**（因为 `best` 初值 0，`0 >= 0` 恒成立，`bestIdx` 永不更新）。

- 调用者：`rich4_ai_use_card.asm` 里 14 处、`rich4_ai_use_tool.asm` 1 处
  （hint 文件的注释 `call 0x40d2d3` 与实测地址**一致**）。
- **未决**：`hostility[a][b]` 的方向语义（a 对 b 还是 b 对 a）在
  `update_hostility` 的调用点里确认；本函数读的是
  `player[self].+0x4c + i*4`，即**自己对他人的敌意**。

## 四之二、★ 敌意表的**写入**：`update_hostility`（`VA 0x0040df69`）

> 2026-09-18 补。上面 §四 讲的是**读**（`find_most_hostile_player` 取敌意最高者），
> 本节是**写**。它此前只在 `magic-house.md` / `gods.md` 的调用点里被顺带提到一句
> 「`+0x4c + 4*b += delta`，夹在 ≥0」——**漏了三个分支**。

全文 38 条 / 113 字节（`gen/db.txt`）：

```asm
0040df69  push ebx / push edi
0040df6b  edx = [esp+0xc]                  ; a
0040df6f  ebx = [esp+0x10]                 ; b
0040df73  cmp edx, ebx / je end            ; ★ ① a == b 直接返回
0040df77  cmp dword [esp+0x14], 0 / jge 加
0040df7e  eax = a*0x68
0040df83  cmp dword [eax + b*4 + 0x496bb4], 0 / je end   ; ★ ② 负增量且当前为 0 → 返回
0040df8d  edi = hostility[a][b]（+0x4c，4 个 dword）
0040dfa1  edi += delta
0040dfa3  hostility[a][b] = edi
0040dfa9  test edi, edi / jge 跳过
0040dfad  hostility[a][b] = 0              ; ★ ③ **只有下限 0，没有上限**
0040dfb5  cmp dword [esp+0x14], 0 / jle end
0040dfbc  cl = byte [a + 0x41]             ; a 的 allied_player（1 基）
0040dfca  cmp ecx, ebx+1 / jne end
0040dfce  push edx / call 0x40cc1a         ; ★④ 敌意**上升**且 b 是 a 的盟友 → **拆盟**
```

| # | 判据 | 结果 |
|---|---|---|
| ① | `a == b` | 原样返回（连同盟都不看）|
| ② | `delta < 0` ∧ 当前 == 0 | 原样返回（与「加到负数再夹」结果一致，只是提前跳出）|
| ③ | 其他 | `hostility[a][b] += delta`，**仅当 < 0 时置 0**；正增量**可以超过 100**（实测 `0 + 500 = 500`）|
| ④ | `delta > 0` ∧ `allied_player[a] == b+1` | 调 `0x40cc1a(a)` = **双向拆盟**（清双方 `+0x41`/`+0x3d` 四格）|

★ 三条容易写错的：

1. **`delta <= 0` 永不拆盟** —— 这就是 `cmp delta,0 / jle` 单独写一遍的原因；
2. **「a 的盟友是自己」触发不了拆盟**：判据是 `allied == b+1`，要它等于 `a+1` 就得
   `b == a`，而 ① 已经先返回；
3. **`b` 没有上界检查** —— `b = 4` 会写到 `+0x5c`（`monthly_paid`），且与正常路径一样
   是**在旧值上累加**（实测 `0x11111111 → 0x11111114`）。实际调用点都只遍历 0..3，
   构造上不可达；复刻加了护栏，登记为**有意偏离**（`rules/hostility.ts` 的注释 +
   `docs/known-deviations.md`）。

**取证方式**：`tests/test_hostility_update.py`（通道 2，**22/22**）在 Unicorn 里
逐条驱动 `0x40df69`，把上面四条 + 越界写全部实测过。

`@source` `VA 0x40df69`、`VA 0x40cc1a`、`VA 0x496bb4`、`VA 0x496b68`、`VA 0x496ba9`、
`VA 0x496ba5`。

4. **買商業用地的行業別随机（#4）此前不在任何既有记录里**；

| 運用比例 | double **0.05** | `0x463cc8` |
| reserve 上限 | **`0x1b58` = 7000** | `0x41d7ee` 立即数 |
| 開局資金 | `[0x49908c]`，由表 `0x46cb94` 写入（`0040717e`） | 表值 = `{300000, 200000, 100000, 50000, 30000, 10000}` |
| 判据返回 | 1 = 买 / 0 = 不买 | `0x41d82d` |

**★ 重要**：买地判据 **不看 hostility、不看 owner、不看 type、不看 `find_most_hostile_player`**
—— 只看「扣掉地价后是否仍高于 reserve」。这与「AI 会针对仇敌」的直觉不同。

**地价的完整算法**（住宅，`0x41a036`..`0x41a050`）：

```asm
0041a036  mov      cl, byte ptr [esi + 0x1a]     ; level
0041a039  xor      edx, edx
0041a03b  mov      dx, word ptr [esi + 0x1e]      ; house_price
0041a03f  imul     edx, ecx                        ; house_price × level
0041a042  xor      ecx, ecx
0041a044  mov      cx, word ptr [esi + 0x1c]      ; land_price
0041a048  add      edx, ecx                        ; land_price + house_price×level
0041a04a  mov      ebp, dword ptr [0x4990e8]      ; price_index
0041a050  imul     ebp, edx                        ; ★ × price_index
0041a053  cmp      ebp, dword ptr [eax + 0x496b84]
0041a059  jg       0x41a159                       ; 现金不够 → 「您的現金不足！」
```

```
住宅 cost = price_index × ( land_price[+0x1c] + house_price[+0x1e] × level[+0x1a] )
商業 cost = price_index × word[+0x22]                      ; 0x41a88c
```

### 6.5 商業用地的等级上限表

商業加盖（`0x41a2b3`）按行業別查上限表 **`0x474940[type]`**，
表值 = `{1, 5, 5, 1, 5}`（子代理读出）；`cost = price_index × word[+0x24]`。
⇒ 行業別 0 与 3 的上限只有 **1 级**（不能加盖）。

### 6.6 股票 / 银行 AI（已定位，阈值部分未决）

| 入口 | 作用 | 关键闸门 |
|---|---|---|
| `0x004284be` 的 AI 分支 **`0x0042886e`** | **股票交易 AI** | `rand()%15`、`rand()%3`、`rand()%4` 三道闸门（`0x42886e` / `0x428a37` / `0x428ae8`） |
| `0x0042bf03` | **银行 AI 第一步** | `rand()%3 == 0` 才继续（`0x42bf14`），且 `0x4521aa(...) >= 0xf` |
| `0x0042c79f` | **卖股**（串「賣出%s%d張」） | `(bank+cash) < loan` 且 `0x4521aa(...) <= 6` → 强制卖股；否则 `rand()%3 == 0`（`0x42c802`） |
| `0x00436b0a` | **银行 AI** | 找 `level == 7` 的銀行建筑 → 强制償還 / 特別融資 |

- ★ **`0x4967e0` 不是持股数组，是「公佈欄挂牌表」**（2026-09-16 订正）：
  **4 玩家 × 7 槽 × 12 字节 = 336 字节**，块内下标 `+0x48` 就是第 7 槽的起点。
  ```asm
  00427edf  imul eax, dword [0x49910c], 0x54   ; eax = 当前玩家 × 0x54（= 7 × 12）
  00427ee6  cmp  byte [eax + 0x496828], 0      ; 0x496828 = 0x4967e0 + 0x48 ⇒ 第 7 槽
  ```
  旧文写作「player × `0x54`，12 档股票」是把**槽的字节数 12** 误当成了**股票档数**；
  真正的持股表是 `0x21f6` 那个（`holdings`），两张表**互不相干**。
  挂/撤/买的槽结构见 `rich4-remake/packages/core/src/places/notice-board.ts`
  （逐个 `@source`）与 `places.md`。
- 银行相关数组：`0x4971a0`（player × `0x60`，12 档）。
- **主動存款/提款 AI 未找到 → 未决**。

#### `0x0042bed0`：卖股用的 **`qsort` 比较器**（`@source` 全函数 20 条，逐条读）`[A]`

```asm
0042bed4  ebx = arg1 / mov bx, word [ebx]     ; ★ 参数是**指针**，比较的是它指向的 int16
0042bedb  edx = arg2 / mov dx, word [edx]
0042bee2  esi = (int16)bx ; ecx = (int16)dx
0042bee8  cmp esi, ecx / jle 跳过
0042beec     eax = 0xffffffff                  ; ★ arg1 > arg2 → −1
0042bef7  cmp ecx, edx / jge 跳过
0042befb     eax = 1                           ; ★ arg1 < arg2 → +1
0042bf02  ret                                  ;    相等 → 0
```

⇒ 按 **`int16` 降序**排序，**相等返回 0**。

★ 两点：
1. **它就是「无调用者」函数的一个典型**：`qsort` 通过函数指针调它，所以
   机械层（`gen/functions.json` 的 `callers`）看到的是 0 个调用者 ——
   与窗口过程、vtable 回调用的是同一个盲点。做覆盖审计时**不能**拿
   「0 调用者」当「死代码」（见 `docs/coverage-by-function.md` 的桶 2/桶 3）。
2. **相等返回 0 ⇒ 并列的先后来由 `qsort` 的实现决定**，而原版那份 `qsort` 是
   **不稳定**的 ⇒ 并列顺序**在原版里就没有定义**。复刻取「同分按下标升序」
   是**明确登记过的选择**（`rich4-remake` 的 **D-006**），不是猜测。

`[未决]`：`rich4-remake/packages/core/src/ai/stock-policy.ts` 的注释另记了
「从头扫：0 分跳过；第 i 名以 `rand()%24 <= 12−i`」—— 本轮**未逐条核**该式
（`0x42bf07` 那支函数只核到 `rand()%3` 闸门与持股总值累加）。
下次做 AI 卖股时应把它钉下来（另：那处 `rand()` 同样消耗全局 PRNG）。

## 八、★ 全文最重要的待复核点：`+0x15` 到底是什么

本文件沿用了既有 `player-struct.md` 的命名「`+0x15` = `who_plays`」，
并在多处把「`+0x15 == 1`」当作「该玩家由电脑操作」。**但本次两个独立子代理
都指出这个判读与指令不符**：

| 观察 | 指令 | 含义 |
|---|---|---|
| 驱动 `0x441baa` 开头 | `0x441bbb cmp dl,1 / jne 0x441d00` | `== 1` 走的是**有 UI 的那条**（建离屏表面、`_Wait_0402_Message`） |
| 商业买地 `0x41a21f` | `cmp byte ptr [eax+0x496b7d],1 / jne 0x41a23e` | `== 1` 走 **`0x440aac`（开面板）**，否则走 `rand()%4+1` |
| 住宅加盖 `0x419986` | `cmp byte ptr [eax+0x496b7d],1 / jne 0x41b077` | `== 1` 时**要求** `0x440ba8` 提示返回 1 才继续 |
| 道具驱动 `0x447da5` | `cmp dl,1 / jne 0x447f82` | 同卡片驱动 |

⇒ 更自洽的解释是：**`+0x15 == 1` 表示「这个座位由『人』操作（真人或托管），
需要走交互确认」**，而 AI 全自动分支是 `+0x15 & 6`（`0x441d00 test dl,6` /
`0x418dd8 test byte [..+0x496b7d],0x30`）。

**本文件的处理**：凡涉及该字段的判据，一律按**指令本身**描述
（写清 `==1` 与 `&6` 各自的去向），**不**把它统一翻译成「电脑/真人」。
`+0x15` 的位定义（bit0 = 座位有人？bit1/2 = ？bit4/5 = ？）**未决**。
