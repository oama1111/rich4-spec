# 数据表总览（Data Tables）

> **真值声明**：本文的唯一真值是 `../../Rich4/rich4.exe`。每一条结构结论都附
> `@source 0xADDR` 与反汇编原文；凡未能实证的一律标 **未决**。
> `rich4-re/` 只作线索，本文不引用其结论。

本文的目标：把 `gen/layout.json` 中 `kind == "table:data"` 的 **104 张数据表**
全部核实并写清结构、语义、证据，让复刻者不必再回汇编里找答案。

## 一、口径与可复算方法

### 1.1 这 104 张表是怎么来的

`gen/layout.json` 由 `tools/rich4strings.py` 生成，其 `table:data` 判据是
**"连续 ≥2 个 4 字节值，每个值都落在 `0x401000..0x4B0000` 内、且多数不是代码段
指针"**（`tools/rich4strings.py:134` 的指针判据 + `:144` 的 `n >= 2` + `:149` 的 `table:code/table:data` 二选一；注意 `0x4B0000` 是**该判据的上界常量**，
不是任何节的边界——节边界见 §1.5）。因此：

* 它检出的是**指针游程（pointer run）**，不是"逻辑表（table）"。
* 游程的**起点**受上一个区域（字符串／普通数据）的结束位置影响，
  所以 `layout.json` 的 `va` **不保证**等于真表的基址。

复算命令（本文件所有计数均由此得出）：

```bash
cd <repo>/rich4-spec
python3 - <<'PY'
import json
L=json.load(open('gen/layout.json'))
tabs=sorted([x for x in L if x['kind']=='table:data'],key=lambda x:x['va'])
print(len(tabs), sum(t['size'] for t in tabs))   # → 104 5820
PY
```
抽样说明「游程 ≠ 逻辑表」的字节真值：

@source 0x463fbd
463fbd  3c 1c 46 00 40 1c 46 00 08 80 45 00 60 92 44 00   ; 4 个「像指针」的 dword
                                                        ; （从浮点常量中间错位 1 字节读起）

**实测：104 张表、合计 5820 字节。**

### 1.2 三级证据

| 级别 | 手段 | 作用 | 局限 |
|---|---|---|---|
| A | `python3 tools/rich4dis.py func 0xADDR` + `gen/db.txt` | 精确指令文本、函数归属 | 见 §1.3：**有覆盖缺口** |
| B | 一次性 Python + `struct.unpack` 直接读 `rich4.exe` 字节 | 表内容的绝对真值 | 只能读静态字节 |
| C | 一次性 Python + `capstone` 在缺口区做线性反汇编 | 补 A 漏掉的指令 | 缺口内含数据时会失步，需逐条人工复核 |
A∪C 合并管线的自检样本（同一条指令的位移两个通道都可命中）：

@source 0x41bd56
0041bd53  imul     eax, eax, 0x68
0041bd56  mov      ebp, dword ptr [eax + 0x480d92]   ; A 通道漏（db.txt 缺口）、C 通道命中

本文的「静态引用点」列 = **A ∪ C**（把 `gen/xrefs.json` 的 disp/imm 与缺口区线性
扫描的 disp/imm 合并，按目标地址归并到表区间）。这一列**是下界而非上界**：
若某表只通过寄存器基址被访问（`lea eax,[base]; mov edx,[eax+ecx*4]`），
它也不会出现在引用列里——§3 的三张大表就是这样被访问的。

### 1.3 ⚠ 方法论发现：`gen/db.txt` / `gen/xrefs.json` 有覆盖缺口

这是本次核实中最重要的发现，**它推翻了"82 张表无任何函数引用"这一初始结论**。

**证据（可直接复核）**：`tools/rich4dis.py` 的递归遍历没有覆盖整个 `AUTO` 段。
`gen/db.txt` 里**不存在** `0x0041bd45` 这条指令：

```bash
grep -c "0041bd4" gen/db.txt      # → 0
```

但它在机器码里真实存在（capstone 从已知边界 `0x41bd36` 线性反汇编）：

```
@source 0x41bd45
0041bd36  mov      ebx, dword ptr [0x49910c]
0041bd3c  cmp      ebx, 4
0041bd3f  jge      0x41c164
0041bd45  imul     eax, ebx, 0x68
0041bd48  mov      al, byte ptr [eax + 0x496b7b]
0041bd4e  and      eax, 0xff
0041bd53  imul     eax, eax, 0x68
0041bd56  mov      ebp, dword ptr [eax + 0x480d92]   ; ★ 引用 Array1 槽 13
0041bd5c  push     ebp
0041bd5d  push     1
0041bd5f  push     ebx
0041bd60  jmp      0x41bb90
```

规模：`gen/db.txt` 全部指令地址排序后，相邻间隔 >16 字节的缺口有 **171 处**，
最大 1220 字节（`0x4125db..0x412a9f`）。例如 `0x41bce6..0x41be1c`（310 字节）、
`0x41bfcd..0x41c161`（404 字节）都是缺口。

**后果**：

1. 只用 `gen/xrefs.json` 判定"无引用"会**漏判**。实测被漏掉的活跃引用至少有：
   `0x480d92/0x480d96/0x480d9a`（Array1 槽 13/14/15）、
   `0x476044`（5 处）、`0x4755f8` 的部分槽位、`0x47511c` 的多数槽位。
2. `docs/systems/tools.md` 对 `0x480d92` 的记述是**对的**（它自己做了反汇编），
   而本文 §1.2 的 A 级证据会把它判成"无引用"——两者不矛盾，是
   `db.txt` 的缺口造成的假象。
3. **建议**（未执行，属 `tools/` 改动，超出本文授权）：`tools/rich4dis.py`
   在递归遍历后对未覆盖的 `AUTO` 区间补一遍线性扫描。

> 因此本文对"是否有引用"一律给出**合并三源的引用列表**，
> 并在只靠 C 级证据得出的结论上标 `（缺口区，capstone 复核）`。

### 1.4 ⚠ `layout.json` 的边界有五类系统性偏差

| 偏差类型 | 实例 | 真值 |
|---|---|---|
| **起点晚了几项**（前面的 dword 被误判成字符串） | `0x480856` | 台詞表真基址 `0x48084a`（差 12 字节 = 3 项） |
| 同上 | `0x476044` | 帮助标签池真起点 `0x476028`（差 28 字节 = 7 项） |
| 同上 | `0x481942`/`0x481ab2`/`0x481c1a`/`0x481d82`/`0x482052` | Array2 各角色首槽，`layout` 从第 2 槽起算 |
| **跨段合并**（把两张相邻表并成一张游程） | `0x480856` 334 项 | 台詞表 321 项 + Array1[0] 前 13 项 |
| 同上 | `0x476044` 94 项 | 帮助标签池 92 项 + 帮助主题表[0] 2 个字段 |
| **把长记录切成碎片**（只把记录里的连续指针当表） | `0x480dc2`(52) 与 `0x480dfa`(12) | 同一记录 `Array1[1]` 的两段（+0 与 +56） |
| **误检**（非指针数据里出现像指针的 4 字节窗口） | `0x463fbd`、`0x470922`、`0x482492`、`0x48457a` | 浮点常量区 / int16 数组 / u16 递增表 |

@source 0x48084a

480856  08 6c 46 00   ; = 0x466c08 `#1053我慘了`      ← layout.json 却从这里起算


### 1.5 自查：节归属与"文本真值"的口径

**（a）节表（用 `python3 tools/rich4dis.py info` 复核，勿凭记忆）**

| 节 | VA 范围 | RawSize |
|---|---|---|
| `AUTO` | `0x401000..0x4613ff` | 394240 |
| `.idata` | `0x462000..0x462dff` | 3584 |
| `DGROUP` | `0x463000..0x489bff` | 158720 |
| `.bss` | `0x48a000..0x499bff` | 64512（文件内无字节） |
| `.reloc` | `0x49a000..0x4a43ff` | 41984 |
| `.rsrc` | `0x4a5000..0x4a59ff` | 2560 |

本文对"某值属于哪个节"的断言只有 §5.4 一处（`0x470922` 那个错位窗口里的 dword 值），
已按上表逐项核对：**该值不在任何节内**，故不是指针。除此以外，本文只断言
"表在 `DGROUP` 内"（可由 `0x463000 <= va < 0x489c00` 直接复核）。

**（b）文本真值：全部取自 `DGROUP`（`strings.json` 的 `trusted == true`），
0 条来自 `AUTO`**

`gen/strings.json` 带 `trusted` 字段：`DGROUP` 段（3115 条）`trusted == true` 是
游戏真字符串；`AUTO` 段（4031 条）是代码段里被**被动解成 Big5 的乱码假阳性**
（例如 `1骼︺qI`），不得当文本真值。本文的取串流程是：

1. 串 VA **只**取自数据表里的指针值（或代码里的直接位移），并断言该 VA ∈ `DGROUP`；
2. 从 `rich4.exe` 的 `DGROUP` 字节做 Big5 解码；
3. 与 `gen/strings.json` 的 `trusted == true` 条目**逐字交叉核对**。

机械核对结果（可复算；统计范围 = §3/§4/§5 点名的全部表项指针）：

```
串 VA 总数                       1538
其中不在 DGROUP 的                  0      ← 故无一条来自 AUTO 段
strings.json 有"同一起点"trusted 条目 1041
  这些条目与本文字节解码结果逐字一致    1041 / 1041（不一致 0）
Big5 解码失败（只给 VA，不引文本）      2    ← 0x46ae77、0x46ae85
其余 ≈495 条落在 strings.json 的"多行串后缀/首行缺失"缺口里，
按 §1.5(c) 以 DGROUP 字节为准。
```

> 复算方式：遍历本文 §3/§4/§5 点名的全部表项指针 → 断言
> `0x463000 <= va < 0x489c00` → 与 `strings.json` 的 trusted 条目比对。

**（c）`strings.json` 自身的两类 artifact（本文已规避，不据此做断言）**

* **多行串被按换行拆开，且首行常常缺失**。例：`0x46484c` 的真串是
  `#0075歡迎光臨\n大富翁銀行！`，而 `strings.json` 只收了后缀
  `0x46485a '大富翁銀行！'`，**首行没有条目**（搜 `歡迎光臨` → 0 命中）。
  因此"某串存不存在"以 **DGROUP 字节**为准。
* **起点偏移**。例：`0x464c2e` 的条目是 `'郈#0096約翰喬'`，比真串起点
  `0x464c30` **早 2 字节**。
* 少数串含**非 Big5 字节**（`0x9D 0xDD` 之类），Big5/CP950/GBK 均解码失败，
  例如 `0x46ae77`（`#0752` 开头）。**本文对这类串只给 VA/语音号，不引用其文本。**

@source 0x46484c
46484c  23 30 30 37 35 c5 77 aa ef a5 fa c1 7b 0a a4 6a   ; '#0075歡迎光臨' + '\n' ...
46485c  b4 49                                             ; ... '大富翁銀行！'
                                        ; strings.json 只有后缀条目 0x46485a '大富翁銀行！'

## 三、三张大表（本文的核心结构结论）

`0x48084a..0x48231a` 这一整片是**三张首尾相接、按角色分块的指针表**：

```
0x48084a ── 台詞表          12 角色 × 27 事件  = 324 项 × 4 = 1296 B  → 0x480d5a
0x480d5a ── Array1 道具台词  12 角色 × 104 B（16 槽）  = 1248 B        → 0x48123a
0x48123a ── Array2 事件台词  12 角色 × 360 B（90 槽）  = 4320 B        → 0x48231a
```

三个基址都 ≡ 2 (mod 4)——**原版的数据段确实存在非 4 字节对齐的指针表**，
这是实测事实（代码里的立即数就是这些地址），复刻时必须照抄。

### 3.1 台詞表 `0x48084a`：12 角色 × 27 事件，步长 108

**结构**：`ptr = *(char**)(0x48084a + 108*role + 4*event)`，`role = 0..11`，`event = 0..26`。

**索引算法（实证）**：`0x40f8a0` 用 `12*role`（`shl 2 / sub / shl 2`）再
`[eax + ebx*8 + base]`，合计 `12x + 96x = 108x`：

```
@source 0x40f889

0040f899  sub     ebx, eax      ; 3x

0040f8a0  mov     ebp, dword ptr [eax + ebx*8 + 0x48084a]   ; ★ 108x

```

## 七、项目点名的两张"已知表"核查

### 7.1 `land +0x20` 租金表 —— **不在** 104 张表内

租金表是**地块结构体的字段**，不是独立数据表，因此不会被
`layout.json` 的指针游程检出（它的内容是 uint16，不是指针）：

```
@source 0x419796
00419796  mov     ax, word ptr [ebx + eax*2 + 0x20]   ; ★ 租金表[level]
```

* 字段：`land+0x20`，`uint16 × 6`（占用 `0x20..0x2b`）。
* `docs/systems/land-rent.md` §「`0x20` 的按等级租金表」已正确记述，
  且该文档的修正说明（`0x2c` 起另有一个 dword）与本次核对一致。
* **结论**：无需在本文重复；`docs/systems/land-rent.md` 仍是该表的主文档，
  本文以本条作为交叉引用。

### 7.2 魔法屋 12 项 × 16 字节表 `0x47571C` —— **不在** 104 张表内

**原因**：该表的 16 字节记录里**只有 `+8` 一个字段是字符串指针**
（`+0`/`+4` 是 int32 图标 x/y，`+0x0C` 全档无读者），
因此不产生"连续指针游程"，`layout.json` 把这段字节判成 `data`：

```
@source 0x47570c
0x4756e8  (layout: data 60 B)  ← 含 0x47570c/0x475710/0x47571c/0x475720
0x475724  (layout: data 16 B)  ← 记录 0 的 +8 名称指针字段
0x475738  (layout: data)
...
```

* 记录基址 `0x47571C`、步长 16、12 项，`+8` = 名称指针
  （`docs/systems/magic-house.md` §三.2 已实证：
  `00432e12 mov edx,[eax+0x475710]`／`00432e20 mov esi,[eax+0x475714]`）。
* 本次**额外核实的两点**（服务于复刻者）：
  1. `0x4756e8` 起是 **12 项 × `(int16 x, int16 y)` 坐标表**（48 字节，
     到 `0x475718`），紧随 20 项字符串表之后：

     ```
     @source 0x4756e8
     004756e8  42 01 5b 00 9e 01 52 00 c5 01 9d 00 fd 01 f2 00   x=322,y=91 / 414,82 / 453,157 / 509,242 ...
     ```
     代码取用方式为 `movsx edx, word ptr [eax*4 + 0x4756e4]`（1 基下标，
     `k=1 → 0x4756e8`）：

     ```
     @source 0x432bd2
     00432bd2  movsx   edx, word ptr [eax*4 + 0x4756e4]
     00432be1  movsx   eax, word ptr [eax*4 + 0x4756e6]
     ```
     与 `docs/systems/magic-house.md` §三.2 的「格座標 k=1..12（1 基）」一致 ✅。
  2. `0x475698` 起的 20 项字符串表**结束于 `0x4756e8`**，
     与坐标表**不重叠**（`0x475698 + 20*4 = 0x4756e8`）——
     即 `layout.json` 的 80 字节边界正好是真边界。

### 7.3 顺带核实：`0x48231a` 的 `{int32,int32}` 8 字节步长表

它不在 104 张表内（`layout` 判为 `data`），但它是 Array2 的**紧邻后继**
且被 **14 个函数**引用，复刻时容易踩坑，故记录观察事实：

```
@source 0x48231a
48231a  00 00 00 00 00 00 00 00 01 00 00 00 00 00 00 00
48232a  02 00 00 00 00 00 00 00 04 00 00 00 00 00 00 00
48233a  03 00 00 00 00 00 00 00 ff ff ff ff 00 00 00 00
```

* 8 字节记录：`{ int32 key, int32 value }`；`key` 实测序列

* **未决**：`key` 的枚举语义与 `value` 的填充时机**未决**。

## 八、已发现并修正的错误清单

### E1 — `places.md` §1.9：台词表基址错了 12 字节（`0x480856` → `0x48084a`）

* **错在哪**：`docs/systems/places.md:228-229`
  > 每角色一块 `27 × dword = 108` 字节，基址 **`0x480856`**（由 `0x44f2c2` 的

  以及 `:234` 的索引表「`0 / 1` → `0x480856 / 0x48085a`」、
  「`16` → `0x480896`」、「`17` → `0x48089a`」。
* **正确值**：**基址 `0x48084a`**；`0x480856 = 0x48084a + 0x0C` 是**事件下标 3**；
  两个随机槽是**事件 3/4**（`0x480856`/`0x48085a`）；

  ```
  @source 0x44f258
  0044f258  mov     ebp, dword ptr [edx + eax*8 + 0x48084a]   ; 基址 0x48084a
  @source 0x44f2ea
  0044f2e8  mov     edx, eax
  0044f2ea  mov     ebp, dword ptr [edx + eax*8 + 0x480856]   ; 0x48084a + 12 = 事件 3
  ```
  再加**全表机械核对**：`0x48084a + 108*role + 4*event` 的语音号
  `= 1050 + 27*role + event`，324/324 项 0 例外（§3.1）。
  若按 `places.md` 的基址（`0x480856`），第 0 行的「第 0 项」会落到 `#1053`，
  与「1050 起」的编号规律矛盾。
* **影响**：`places.md` 的槽号整体偏移 3；`0x48089e`(事件21)、`0x4808a2`(22)、
  `0x4808a6`(23) 等被 `cards.md`/`gods.md` 引用的位移**地址本身没错**，
  但若按 `places.md` 的"基址"换算事件号会全部偏 3。

### E2 — `news.md` §432：台词表步长写成 `0x24`（应为 `0x6C`）

* **错在哪**：`docs/systems/news.md:432`
  > owner 台词用 `player_say(owner-1, 2, ...)`：`2` 是「情境槽」编号，
  > 台词取 `0x480856 + char*0x24 + (rand()&1)*4`。
* **正确值**：`0x48084a + char*0x6C + 事件*4`，此处事件 = 3 或 4
  （即 `0x480856 + char*0x6C + (rand()&1)*4`）。
* **验证**：
  ```
  @source 0x4494bc
  004494a5  shl     eax, 2
  004494a8  sub     eax, edx
  004494aa  shl     eax, 2
  004494ad  mov     ebx, eax
  004494af  shl     ebx, 3
  004494b2  add     ebx, eax        ; ebx = 12*char + 96*char = 108 = 0x6C
  004494b4  call    0x456f2d
  004494b9  and     eax, 1
  004494bc  mov     edx, dword ptr [ebx + eax*4 + 0x480856]
  ```

### E3 — `fortune.md`/`cards.md`/`gods.md` 的"槽"表述不统一（建议而非硬错）

* **现象**：`fortune.md:626/897` 写「`player_say(cur, 2, 槽 0x480856)`」、
  `cards.md:2145` 写「表 `0x48089e[character*0x6C]`」、

### ★ 事件表的 `blessing` 字段：28 个事件带「神明加持」（2026-09-17 补，第 37 条）
