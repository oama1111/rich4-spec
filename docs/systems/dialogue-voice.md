### ★ 关键规律：`#NNNN` 就是语音资源号

**★ 先分清两件事（早期版本在这里过度推广，造成过一个实质错误）：**

| | 是什么 | 取值范围 | 来源 |
|---|---|---|---|
| **`#NNNN` 前缀的语义** | **直接**就是 `speaking.mkf` 的资源号，**没有任何偏移** | **0..1373** | 文本字面量 |
| **角色台词表 `0x48084a`** 的编号规律 | `1050 + 角色下标 × 27 + 事件下标` | `1050..1373`（324 条） | 代码生成 / 表的字面量 |

即：`1050 + 角色×27 + 事件` 只描述**角色台词表**这 324 个条目**用的是哪些号**，
**不是** `#NNNN` 的解析规则。`#NNNN` 的解析规则是**原样取值**（见下）。

```
角色台词表（VA 0x0048084a）：语音资源号 = 1050 + 角色下标 × 27 + 事件下标
            1050 + 11×27 = 1347   ← 角色 11 的起始，与实测吻合
            1050 + 12×27 = 1374   ← 表的末端（不含）
```

`speaking.mkf` 共 **1,374 个块**（编号 **0..1373**；`extracted/Speaking/meta.json`
的 `nchunks = 1374`）—— 角色台词表占用的 `1050..1373`（共 324 个）落在范围内且一一对应。

### ★ 全代码段只有**两处**解析 `#`，且**两处都零偏移**

为把"`#NNNN` 原样取值"这条结论钉死，本轮**穷举**了整个代码段里与 `0x23`（`'#'`）
比较的指令，只有两处是**文本前缀解析**：

| 解析点 | 函数 | 汇编 | 说明 |
|---|---|---|---|
| `0x0044fb00` | `0x0044fabc`（通用文本绘制） | `cmp ah, 0x23` | 串**中间**出现 `#` 也处理 |
| `0x0044f07c` | `0x0044ef41`（`player_say`） | `cmp byte ptr [ebx], 0x23` | 只处理**串首** `#` |

（另有 `0x45b30b` / `0x448be2` / `0x43380a` / `0x44bb4b` / `0x4402d7` 处
与 `0x23` 的比较，是**数值 35 的比较**，与 `'#'` 字符无关。）

而 `play_speech`（`VA 0x0045441a`）在整个代码段里**只有两个调用点**，
正是上面两处（`0x0044f136` 与 `0x0044fb4e`）—— **没有第二条语音路径**。

`player_say` 的解析（`@source 0x0044f0ed`–`0x0044f136`）：

### 角色 11（金貝貝）不说人话

它的串是 `#NNNN@DD` 形状，`@DD` 是**表情图号**（两位数）。
**★ `#NNNN` 照样要播**——`@DD` 只是**追加**一件事（画表情图），
两者**不是二选一**（见上面的 `player_say` 反汇编：`play_speech` 在 `push eax` 之后
才继续走画表情图的分支）。复刻时把这类串的语音置空是**错的**。
解析在 `player_say` 内（`VA 0x0044f08d`）：

```asm
0044f08d  cmp  byte ptr [edx], 0x40        ; '@'
0044f090  jne  0x44f140
0044f098  mov  al, byte ptr [edx + 1]      ; 十位
0044f09b  lea  ecx, [eax - 0x30]
; … eax = 十位*10 + 个位
0044f0b5  push 0x82 / push 0xf0            ; 绘制坐标 (130, 240)
0044f0c2  mov  eax, edx                    ; edx = 图号 - 1
0044f0c4  shl  eax, 2 / sub eax, edx       ; ×3
0044f0cb  shl  edx, 2                      ; ×4  → 共 ×28
0044f0ce  mov  eax, dword ptr [0x48bad4]   ; 表情图表基址
0044f0d3  add  eax, 0xc                    ; +12
0044f0d6  add  eax, edx                    ; + (图号-1)*28
0044f0e0  call 0x456418                    ; 绘制
```

**表情图记录步长 = 28 字节**（`×3` 再 `×4`），基址 `[0x48bad4] + 0xc`。

## 一之二、★ 事件号由**阈值阶梯**选出（不是直接传入）

这是本轮最重要的补充：**调用方不传事件号**，而是传一个"严重度"数值，
由两个孪生函数按**阈值阶梯**映射到 6 个基础事件。

### 好消息阶梯：`VA 0x0044f230`（6 处调用）

```asm
0044f238  mov  edx, dword ptr [esp + 0x18]   ; arg2 = 严重度
0044f23f  cmp  edx, 0x64                      ; 100
0044f242  jle  0x44f262
; ── arg2 > 100 ──
0044f246  mov  dl, byte [eax + 0x496b7b]      ; player.character
; … offset = char*12 + char*96 = char*108
0044f258  mov  ebp, [edx + eax*8 + 0x48084a]  ; ★ 事件 0（char*108 + 0）
0044f262  cmp  edx, 0x32                      ; 50
0044f265  jle  0x44f292
; ── 51..100 ──
0044f27b  shl  ebx, 3 / add ebx, eax          ; ebx = char*108
0044f280  call 0x456f2d                       ; ★ rand15()
0044f285  and  eax, 1                         ; ★ 取 0 或 1
0044f288  mov  edi, [ebx + eax*4 + 0x48084a]  ; ★ 事件 0 或 1（随机）
0044f292  test edx, edx
0044f294  je   0x44f2bd                       ; arg2 == 0 → 不说话
; ── 1..50 ──
0044f2aa  mov  ecx, [edx + eax*8 + 0x480852]  ; ★ 事件 2（+8 = 2×4）
```

### 坏消息阶梯：`VA 0x0044f2c2`（4 处调用）

同一套结构，但断点是 **6 / 3**：

```asm
0044f2d1  cmp  edx, 6
0044f2d4  jle  0x44f2f4
; ── arg2 > 6 ──   → 事件 3
0044f2f4  cmp  edx, 3
0044f2f7  jle  0x44f324
; ── 4..6 ──       → 事件 4
0044f324  test edx, edx
0044f326  je   0x44f34f                       ; 0 → 不说话
; ── 1..3 ──
0044f33c  mov  ecx, [edx + eax*8 + 0x48085e]  ; ★ 事件 5（+0x14 = 5×4）
```

#### ★★ 这条规格对「1:1 确定性复现」的意义（重要）

上面 5 个函数里有 **4 处 `call rand`**（A/B/C 的中间档各一次、判据 D 一次、判据 E 一次）。
它们**消费的是同一个全局 PRNG**，而这条链路属于**表现层**（说什么台词）——
也就是说：

> **原版的全局随机序列是「规则 + 表现」共用的。**
> 只要玩家触发过一次中间档台词，之后所有随机事件就已整体位移。

⇒ 无头确定性引擎**不可能**逐位对齐原版的全局序列；能对齐的只有
**规则相关**的那部分消费（拍卖开价的 2N 步、前瞻岔路的 1 步、骰子…）。
复刻本项目把台词选择做成**纯确定性**（中间档一律取 `rand()&1 == 0` 那一支），
登记为 `T-052` 的「有意偏离 1」——**这不是缺陷，是必然**。
写复刻时若想「把它补成随机的」，只会把规则层的序列推歪。

## 二、`player_say`（`VA 0x0044ef41`）

被调用 **112 处**，分布在 **76 个函数**中（`gen/rel32-calls.json` 的
`0x0044ef41` 键）。⚠️ `gen/functions.json` 的 `callers` 字段在此**不完整**
（这也是我建 `rel32-calls.json` 的原因之一）。

### 重要的前置闸门：睡眠/消失/梦游中不说话

```asm
0044ef74  imul eax, dword ptr [esp + 0x24], 0x68   ; 玩家下标
0044ef79  cmp  byte ptr [eax + 0x496b9b], 0        ; +0x33 days_disappearing
0044ef80  jne  0x44f228                             ; 非 0 → 直接返回
0044ef86  cmp  byte ptr [eax + 0x496b9f], 0        ; +0x37 days_sleep_walking
0044ef8d  jne  0x44f228
0044ef93  cmp  byte ptr [eax + 0x496b9e], 0        ; +0x36 days_sleeping
0044ef9a  jne  0x44f228
```

即：**玩家处于「消失 / 梦游 / 睡眠」状态时，`player_say` 直接返回，不出台词也不出语音。**
复刻若漏掉这三个闸门，睡着/梦游的角色会说话 —— 与原版不符。

### 台词表的读取与展示

`0x48084a` 被 **8 处**代码引用（`0x40f8a0`、`0x40fa51`、`0x4154be`、
`0x41bcd3`、`0x44c5b5`、`0x44d862`、`0x44f258`、`0x44f288`），
其中 `0x44f258`/`0x44f288` 就在 `player_say` 内。

此外 `player_say` 会读 `player+0x69/0x6a/0x6b`（坐标）并调 `0x41d476`
（`VA 0x0041efa4` 附近）做说话动画。

### ★★ 第二个实参（`flag`）**函数体里一次都没读**（2026-09-19 实证）

各调用点传的值并不一致 —— 卡 1/2/15/16 传 `3`、卡 22/23 传 `0`，早期文档据此
猜过「显示样式/端口不同」。实测**不是**：

```
$ awk '/^# 0x0044ef41 /{f=1} f&&/^# 0x/{exit} f{print}' gen/db.txt | grep -c 'esp + 0x28'
0
```

`player_say` 共 235 条指令，`[esp+0x28]`（= 第 2 个实参）**零命中** —— 那是个
**遗留形参**。故复刻侧**不需要**建模它（`client/src/speech.ts` 的
`cardPlaySpeech()` 只用「出牌者 + 卡号」两项）。

### ★★ 卡牌使用者台词走**另一张表**：`0x48123a`（槽 0..29）

上面那条「台词表」指的是 `0x48084a`（行距 108，27 槽，受击/情境台词）。
每张卡自己那句在 **`0x48123a`**（行距 **360**，90 槽）里，槽号 = **卡号 − 1**：

```asm
; 送神符 @0x444d0e（26 张卡各一处，槽号与卡号一一对应）
00444d0e  mov  ebp, dword ptr [eax + 0x48128e]   ; = 0x48123a + 4×21
00444d15  jmp  0x44305e                           ; → player_say(cur, 0, 台词)
```

**机械扫 30 个卡片函数体**（`rich4-spec/tests/test_god_charm_cards.py` 的 `[M]` 段）：

| 项 | 结果 |
|---|---|
| 读该表的卡片 | **26 / 30**（1..17、22..30）|
| 不读的 4 张 | **正是四张被动卡** 18 復仇 / 19 嫁禍 / 20 免費 / 21 免罪（`card_functions[N]` 是空桩 `0x4420d5`，本来就打不出去）|
| 读到的槽 | **恒等于 `卡号-1`**（26/26 无例外）|
| 语音号 | 串头 `#NNNN` 恒 = `426 + 52×角色 + (卡号-1)`（360 条无例外）|

> ⚠️ **复刻侧此前整张缺失**（`@rich4/data` 只有 `0x48084a` 那张表），
> 导致用卡时**一个字都不说、语音也不响**。2026-09-19 已补齐：
> 数据在 `packages/data/src/card-lines.ts`（生成脚本 `tools/gen-card-lines.py`），
> 触发通道是 `GameState.lastCardPlay`（core 的纯表现提示字段）+ 客户端的
> `cardPlaySpeech()`（含上面那三道闸门）。取证与清单见
> `rich4-remake/docs/gaps/README.md` §7.89(2)/§7.90。

#### 未决（卡牌台词表）

1. 槽 30..89（每角色另外 22 条非空槽）**尚未逐条接线** —— `data-tables.md`
   §3.3 已列出槽序与触发点，但复刻侧目前只接了卡牌那 30 条。
2. `player_say` 内部的「同一句不重播」闸门（`cmp ebx,[0x4762c8]` / `je 0x44f228`：
   文本指针与上一条相同就直接返回）复刻侧**未建模** —— 现有实现只保证
   「同一次用卡不重复播」。**连续两次说同一句**（同一角色连出两张同样的卡、
   或两个同角色玩家先后说同一句）在原版会**只响一次**。

## 三、★ 语音播放：`play_speech`（`VA 0x0045441a`）

```asm
0045441a  push ebx / push esi
0045441c  cmp  dword ptr [0x47e748], 0     ; _rich4_dsound_ptr
00454423  je   0x454490                    ; 无声卡 → 直接返回
00454425  cmp  byte ptr [0x49715b], 0      ; ★ 配置项 cfg+3（语音开关）
0045442c  je   0x454490                    ; 关闭 → 直接返回
0045442e  call 0x454493                    ; 先停掉上一条语音
00454437  mov  ecx, dword ptr [esp + 0x14] ; ★ 语音资源号
0045443c  mov  ebx, dword ptr [0x48a054]   ; ★ _rich4_speaking_mkf
00454443  call 0x450441                    ; read_mkf
0045444e  call 0x453dcf                    ; 建 IDirectSoundBuffer
00454456  mov  dword ptr [0x47e750], eax   ; 存当前语音 buffer
00454472  call dword ptr [edx + 0x30]      ; ★ IDirectSoundBuffer::Play
```

签名：`play_speech(uint32 speaking_mkf_resource_id)`

**两个调用点**（`gen/rel32-calls.json` 的 `0x0045441a` 键）：

| 调用点 | 宿主 | 语义 |
|---|---|---|
| `0x0044f136` | `player_say` | 台词表分支：`#NNNN` 解析出的号 |
| `0x0044fb4e` | **`drawText_colorcode`** | 绘制任意含 `#NNNN` 的串时触发 |

### ★ 纠正：`#NNNN` 是语音号，不是颜色码

`drawText_colorcode`（`VA 0x0044fabc`）里的 `#` 处理（`VA 0x0044fb00`）：

```asm
0044fb00  cmp  ah, 0x23          ; '#'
0044fb03  jne  0x44fb59
0044fb05  …                      ; 取 [ebx+1..ebx+4] 四位十进制 → eax
0044fb4d  push eax
0044fb4e  call 0x45441a          ; ★ play_speech(解析出的号)
0044fb56  add  ebx, 5            ; ★ 跳过 "#NNNN" 前缀
0044fb59  mov  eax, dword ptr [0x4762cc]
```

**结论**：`#NNNN` 是**内嵌在显示文本里的语音控制码** —— 播放语音号 `NNNN`，
自身不显示。它**与颜色无关**。

真正的文字颜色来自**全局变量**（`VA 0x0044fcd5` 附近：
`mov esi, dword ptr [0x4762e4]` 之后 `push esi` → `SetTextColor`），
以及函数参数；**不是**从 `#NNNN` 解出的。

> 本项目先前在 `render-api.md` 与 `03-annotated-db.md` 里把该前缀写成"颜色码"，
> **是错的**，现已修正。这条也解释了为什么 `#0428讓我把它據為己有！！`
> 能成立：`0428` = 语音资源 428（在 0..1049 区间，属**事件/系统语音**，
> 非角色台词），`讓我把它據為己有！！` 才是显示文本。

## 四、★ 语音资源的真实来源（**本节修正过一次重大错误**）

> ⚠️ **早期版本把 `0x48a05c` 当成了 `speaking.mkf`。这是错的。**
> 由启动装载序列（`VA 0x00401721`–`0x00401764`）逐指令确证：

| MKF 句柄全局 | **文件** | `read_mkf` 读取点 |
|---|---|---|
| `0x48a0e4` | **`data.mkf`**（602 个资源，索引 0..601） | **82 处** |
| `0x48a05c` | **`panel.mkf`**（113 个资源，索引 0..112） | **71 处** |
| `0x48a058` | `effect.mkf`（115 个资源） | 4 处 |
| **`0x48a054`** | **`speaking.mkf`**（1,374 个资源，索引 0..1373） | **1 处** |

```asm
00401721  push 0x46303e  «data.mkf»     ; → mov [0x48a0e4], eax
00401733  push 0x463047  «speaking.mkf» ; → mov [0x48a054], eax
00401745  push 0x463054  «panel.mkf»    ; → mov [0x48a05c], eax
00401757  push 0x46305e  «effect.mkf»   ; → mov [0x48a058], eax
```

### 结论一：**语音只有一个来源**

`speaking.mkf` 的**唯一**读取点是 `play_speech`（`VA 0x0045443c`，
见 §三），资源号来自文本里的 `#NNNN`。**没有第二套语音路径。**

### 结论二：`100 + 角色` **不是语音，是角色头像**

早期版本把 `VA 0x00407660` 的 `lea eax, [ebp + 0x64]`（`ebp` = `player.character`）
读作"角色报名语音"。**实为 `panel.mkf` 的角色头像图素**：

- `100 + 角色`（角色 0..11 → 资源 **100..111**）
- 恰好落在 `panel.mkf` 的 **0..112** 范围内 ✓
- 若它是语音（`speaking.mkf`），资源号 100..111 落在那里的确是**另一段非角色语音**
  （见 §一：`#NNNN` 原样对应资源号，0..1049 段存在）；
  但 `0x407660` 这一处读的是 **`0x48a05c` = panel.mkf**（见 §四 句柄表），
  所以它是**图素**：`100 + 角色` = 角色头像 100..111，落在 panel.mkf 的 0..112 内**严丝合缝**

### 结论三：早期版本列出的「硬编码语音号」是 **panel.mkf 的 UI 图素号**

`0x4e`/`0x4f`/`0x50`…`0x5f`、`0x1a`…`0x1d`、`0x3f`…`0x48`、`0x64+角色` 这些，
**全部落在 `panel.mkf` 的 0..112 内**，是各界面自己的**面板/按钮图素**，
不是语音。（同理，`0x219`(537)、`0x218`(536) 这些落在 **data.mkf** 的 0..601 内，
是数据图素 —— 见 `game-loop.md` §四之二 的落点分派表。）

### 结论四：`speaking.mkf` 的 0..1049 **有静态读取者**（★ 已修正）

**早期版本的错误结论**：「`#NNNN` 只用到 1050..1373，故 0..1049 这 1,050 个语音
资源没有任何静态读取点，属残留资源或运行时计算 → 未决。」

**这是过度推广造成的实质错误。** 事实（`VA 0x0044fabc` 的解析代码见 §一）：
`#NNNN` 是**原样取值**的资源号，文本里**确实**出现 610 个低于 1050 的编号：

```
#0004歡迎下次再來！    (@source 0x4642b4)
#0010謝謝惠顧！        (@source 0x464334)
#0014拜拜！祝您中獎！  (@source 0x4643f9)
#0036行動要快喔！      (@source 0x464530)
（#0500 … #1049 … 共 610 个不同编号）
```

并且这些资源在 `speaking.mkf` 里都是**完整的 RIFF/WAVE**（实测抽样）：

| 资源号 | 文件 | 大小 | 头 |
|---|---|---|---|
| 4 | `extracted/Speaking/0004.bin` | 29,386 | `RIFF` ✅ |
| 10 | `0010.bin` | 18,508 | `RIFF` ✅ |
| 36 | `0036.bin` | 21,438 | `RIFF` ✅ |
| 100 | `0100.bin` | 23,978 | `RIFF` ✅ |
| 500 | `0500.bin` | 56,020 | `RIFF` ✅ |
| 1049 | `1049.bin` | 8,206 | `RIFF` ✅ |

**修正后的结论**：`speaking.mkf` 的 **0..1373 走的是同一条静态读取路径**
（`play_speech(0x45441a)` ← 文本 `#NNNN` ← `0x44fabc`），
其中被文本字面量用到的是 **842** 个不同编号（`4..1373`）。
真正**未决**的只剩「本版文本里没有字面引用的那约 532 个块」——可能由运行期拼接，
或属于未使用的其它语言版本资源。

> 教训：**一个公式对某一个表成立，不代表它对同一符号的所有出现都成立。**
> `1050 + 角色×27 + 事件` 描述的是**角色台词表**，不是 `#NNNN` 的语法。

### 每屏预载的 buffer 全局（**是 panel.mkf 图素，不是语音**）

以下全局存放**按界面预载的 `panel.mkf` 图素 buffer 指针**：

`0x48a354` `0x48a3b8` `0x48a3bc` `0x48a38c` `0x48bd3c` `0x48bcd0`
`0x48bd30` `0x48bce4` `0x48c35c` `0x48c368` `0x48c358` `0x48c398`
`0x48c394` `0x48c3c0` `0x48c270` `0x48be04`

> ⚠️ **修正**：早期版本说这些是"**语音** buffer"。它们来自 `0x48a05c`
> 的读取（= **panel.mkf**，见 §四），因此是**界面图素**。
> 语音**没有**"每屏预载"这一层 —— `play_speech` 每次**按需**从
> `speaking.mkf` 读一个 WAV（`VA 0x00454443`），播完即弃。

**这仍与效果音的设计思路一致**（都是"进入界面预载资源、离开释放"），
只是预载的东西一个是**面板图素**、一个是**音效 buffer**。

| 项 | 值 |
|---|---|
| 大小 | **56,953,526 字节（约 54 MB）** |

### 格式已解析（A 级）

全部 1,374 个 WAV 的 `fmt ` 块：

| 项 | 值 |
|---|---|
| 编码 | **PCM（`wFormatTag = 1`）** |
| 声道 | **单声道（1）** |
| 位深 | **8 位** |

⚠️ **采样率逐文件不同**（有 190 个是 44.1kHz）——
所以**必须按每个文件的 `fmt ` 块播放**，不能用全局固定采样率。
`Speaking.mkf` 目录下另有 1 个 `meta.json`（解包产物，非游戏资源），
故实际 WAV 数为 **1,374**（不是 1,375）。

`Rich4/InstOK.wav`（16,516 字节）与 `InstSel.wav` 是**安装程序**的音效，
**不来自 `Speaking.mkf`**，且是 **16 位** —— 与游戏内的 8 位不同。

## 六之二、语种与区域差异（**目标明确要求的一节**）

### 结论：本版本是**单一语种（繁体中文）**，无运行时语言切换

**证据（三条，均为机械核对）**：

1. **字符集单一**：exe 内 **6,327 条含中文字符串**，
   **零条含常见简体字**、**零条含日文假名**。全部按 **Big5** 解码成功。
2. **配置项里没有语言字段**：`RICH4.CFG`（72 字节）的字段已全部定名
   （见 `ui.md` §一），分别是游戏速度 / 动画开关 / 音乐音量 / 音效音量 /
   自动存档 / 视角 / 日期 / 28 个热键 —— **没有语言项**。
3. **代码里没有语言分支**：字符串读取路径只有 Big5（`gen/db.txt` 里无
   GB2312 / Shift-JIS / Unicode 解码路径）。

### 那 4 个 `FLY*.AVI` 不是语种，是**目的地**

`Rich4/` 下有 `Flytw.avi` / `Flychina.avi` / `Flyjp.avi` / `Flyus.avi`
—— 容易误认成"语种选择"。**实测不是。**

`VA 0x004750e8` 是一张 **4 项文件名指针表**：
`[FLYTW.AVI, FLYCHINA.AVI, FLYJP.AVI, FLYUS.AVI]`，
被 `VA 0x00415944` 引用：

```asm
0041591e  cmp  word ptr [0x4991b6], 0        ; game_stage
00415926  je   0x415936
00415928  push 1 / push 0x46cadc / push 0x4637d8   ; stage != 0 → "AIRPLANE.AVI"
00415934  jmp  0x41594c
00415936  push 1 / push 0x46cadc
0041593d  movsx eax, word ptr [0x4991b8]     ; ★ game_map（0..3）
00415944  mov  ecx, dword ptr [eax*4 + 0x4750e8]  ; ★ 目的地影片
0041594b  push ecx
0041594c  call 0x451677                       ; 播 AVI
```

**语义**：`stage == 0` 时按 `game_map`（0..3）播放"飞往该地区"的动画
（台湾 / 中国大陆 / 日本 / 美国 —— 正是**第一关的四个目的地**）；
`stage != 0` 时播 `AIRPLANE.AVI`。
**与语言无关**，是**关卡内容**。

本目录**只有 v3.11 繁体中文版**一个样本，因此：

- ❌ **无法确定**：是否存在**其它语言版本**（如简中/日文版）的 exe，
